---
id: FR-070
title: "Show the activities of a request and their details"
---

## Requirement

- **Statement:** The conversation shows the activities of a request in the order they happen. An activity shows what the system did and its state. A planned activity appears only when the system produced a plan. No activity is invented. The user can read the detail of one activity and hide it again. The user can hide the activities and read the status message alone. These are viewing actions: they change no activity, start no request, change no slide and stop nothing. The activities stay in the conversation after the request ends. The system shows no planned activity as completed. A failed activity does not by itself make the request fail. A result the system did not confirm shows as neither completed nor failed. The status message shows the state of the request. It shows the cause of a stop or a failure when known. It shows the main impact on the finished work and the next action when they are known. Each shows once. The system invents no cause, no count of completed slides and no outcome of an unfinished activity. The activity detail adds the information known about one activity, such as a technical failure detail. The system shows no second message that repeats them.
- **Updated at:** 25-10-2026

## Acceptance conditions

### AC-1 · Activities show in order while the request runs

- **Given:** A deck of six slides. The user sent "shorten slide 3 and add a slide on risks after slide 4". The system produced a plan: update slide 3, create the risk slide and check the result. It read the deck and started to update slide 3.
- **When:** The user reads the status message and the activities.
- **Then:**
  - The conversation shows the activities in the order they happened.
  - The activities that ended show as completed.
  - The activity that updates slide 3 shows as running.
  - The activity that creates the risk slide shows as planned.
  - The activity that checks the result shows as planned.
  - The status message says what the system is doing now.
- **Check:** deterministic

### AC-2 · Planned work is not shown as done

- **Given:** The state of AC-1. The system finished updating slide 3 and has not started the risk slide.
- **When:** The user reads the activities.
- **Then:**
  - The activity that updates slide 3 shows as completed.
  - The activity that creates the risk slide shows as planned.
  - No activity that did not start shows as running or completed.
  - The activities give no count of completed work beyond their states.
- **Check:** deterministic

### AC-3 · The activities can be hidden and shown

- **Given:** The state of AC-1.
- **When:** The user hides the activities, then shows them again.
- **Then:**
  - With the activities hidden, the status message is in the conversation.
  - The request still runs. The activity that updates slide 3 still runs.
  - No activity changes state. No slide changes. No request starts. The request is not stopped.
  - With the activities shown again, each activity shows its current state.
- **Check:** deterministic

### AC-4 · Activity detail explains the work

- **Given:** The state of AC-2. The system knows what slide 3 says after the change.
- **When:** The user reads the detail of the completed activity on slide 3.
- **Then:**
  - The detail says what the activity did and what it produced.
  - The detail uses words a presentation user understands.
  - The detail shows no key, credential or other secret.
- **Check:** judged

### AC-5 · Reading a detail changes nothing

- **Given:** Two runs. In the first, the state of AC-4. In the second, the state of AC-9.
- **When:** In each run, the user reads the detail of one activity and hides it again.
- **Then:**
  - In each run, the activities and their states are the same as before.
  - In each run, the deck is the same as before.
  - In each run, no request starts and no activity starts.
  - In the first run, the request still runs.
  - In the second run, the request is still failed and is not sent again.
- **Check:** deterministic

### AC-6 · The request waits for an answer

- **Given:** The state of AC-2. The system needs an answer about the risk slide and asks a question.
- **When:** The user reads the activities while the system waits.
- **Then:**
  - The status message says that the system waits for the answer.
  - No activity shows as running.
  - The activities that ended show as completed.
  - The conversation shows no second message that says the system waits.
- **Check:** judged

### AC-7 · The activities stay after the request ends

- **Given:** The state of AC-2. The system finished updating slide 3 and creating the risk slide.
- **When:** The request ends.
- **Then:**
  - The status message says that the work on the request is done.
  - The completed activities stay in the conversation.
  - No activity shows as running.
  - The user can read the detail of each completed activity and hide it again.
- **Check:** deterministic

### AC-8 · A stop keeps the activities that ended

- **Given:** The state of AC-1. The user stops the request while the system updates slide 3.
- **When:** The user reads the conversation.
- **Then:**
  - The status message says that the response was interrupted. It does not say that the work failed.
  - The activity that ended before the stop shows as completed.
  - The activity that updates slide 3 shows as stopped.
  - The detail of that activity says that the user stopped the request.
  - The activities that did not start show as planned.
  - No activity shows as running.
  - The status message gives the number of slides changed once, as FR-026 says.
  - The conversation shows no second message that repeats the interruption or the count.
- **Check:** judged

### AC-9 · A failure keeps the activities that ended

- **Given:** The state of AC-1. The model provider returns an error while the system updates slide 3, and the request cannot finish.
- **When:** The user reads the conversation.
- **Then:**
  - The status message says that the work did not finish.
  - The status message says why, when the system knows it [FR-019].
  - The activity that ended before the failure shows as completed.
  - The activity that updates slide 3 shows as failed.
  - No earlier activity shows as failed.
  - The activities that did not start show as planned.
  - The detail of the failed activity adds the technical detail when the system has it.
  - The status message gives the changed slides once. It gives no number it does not know [FR-026].
  - The conversation shows no second message that repeats the failure, the reason or the count.
- **Check:** judged

### AC-10 · Reopening the chat shows the activities again

- **Given:** Chat X holds a request that ended before it finished, in three separate runs. The user stopped it. It failed. DeckAgent closed during it. Its conversation shows the activities and their states.
- **When:** The user opens chat X again.
- **Then:**
  - The conversation shows the same activities.
  - A completed activity stays completed. A failed activity stays failed. A stopped activity stays stopped.
  - An activity whose final result was not confirmed shows as neither completed nor failed.
  - No activity shows as running.
  - No request starts.
  - The user can read the detail of each activity.
- **Check:** deterministic

### AC-11 · An activity fails and the request goes on

- **Given:** A deck of six slides. The user sent "shorten slide 3 and add a slide on risks". The system produced a plan and started to work.
- **When:** One activity of the request fails, and the request goes on.
- **Then:**
  - The failed activity shows as failed.
  - The failed activity does not show as completed.
  - No other activity shows as failed because of it.
  - The status message does not say that the request failed.
  - The request stays active until its work ends.
  - The detail of the failed activity gives its result when the system knows it.
- **Check:** judged

### AC-12 · A result the system did not confirm

- **Given:** The system updates slide 3 of a deck. DeckAgent ends before it confirms the result of that activity.
- **When:** The user opens the chat again.
- **Then:**
  - The conversation says that the earlier request did not finish.
  - An activity with a confirmed completed state stays completed.
  - An activity with a confirmed failed state stays failed.
  - The activity whose result was not confirmed shows as interrupted.
  - It does not show as completed and does not show as failed.
  - It gives no failure reason.
  - No request starts.
- **Check:** judged
- **Why:** the "interrupted" state for an activity whose result the system did not confirm is precision the author added. The approved decisions say only that the result is never invented.

### AC-13 · Reloading the interface keeps the activities current

- **Given:** The state of AC-1. DeckAgent runs.
- **When:** The user reloads the Local Web interface.
- **Then:**
  - The request still runs.
  - The activities show their current states.
  - No notice says that the work failed or was interrupted.
  - No activity runs again, and no activity repeats in the conversation.
- **Check:** deterministic

### AC-14 · A request with no plan has no planned activity

- **Given:** A deck of six slides. The user sent "shorten slide 3". The system produced no plan. It read the deck and started to update slide 3.
- **When:** The user reads the activities while the request runs.
- **Then:**
  - The conversation shows the activities that started.
  - The activity that updates slide 3 shows as running.
  - No activity shows as planned.
  - The status message says what the system is doing now.
- **Check:** deterministic

### AC-15 · A request with no recorded activity

- **Given:** Three separate runs. In each run, no activity record exists, including no planned activity. In the first, the provider refuses the request before any activity starts. In the second, the request ends and the system recorded no activity. In the third, the system waits for a clarification before doing any activity.
- **When:** The user reads the conversation in each run.
- **Then:**
  - In each run, the status message shows the request state.
  - In each run, the timeline shows no activity.
  - In each run, the system invents no activity.
  - In each run, an empty activity history is shown as empty, not as a missing or failed request.
- **Check:** judged

## Notes

- The status message itself is covered by FR-012. The stop, the failure and the wait are covered by FR-018, FR-019 and FR-020. The reason and the counts appear in the status message, as FR-019 and FR-026 say. The activity detail adds technical detail about one activity.
- The slides that a stop or a failure keeps are covered by FR-025. A reload of the interface is covered by FR-068.
- A planned activity appears only when the system produced a plan. A request with no plan has no planned activity, and a request with no activity has an empty timeline.
- An outline that the system did not finish is never offered for confirmation, as FR-047 says. The activity that drafted it shows as failed, stopped or interrupted, not as completed.
- This requirement sets no rule about trying the same operation again inside one request. It records what the system did, and that record never becomes a retry rule.
- The system does not need a separate activity for every internal call, and the detail does not show model reasoning.
- How the system records an activity is not part of this requirement.
- The explicit `interrupted` activity state (AC-12, _STYLE.md term table) marks an unconfirmed result. The requirement says only that an unconfirmed result is never invented; the term matches that boundary.
