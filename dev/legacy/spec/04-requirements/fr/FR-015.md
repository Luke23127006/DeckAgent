---
id: FR-015
title: "When a request can be sent"
---

## Requirement

- **Statement:** The system offers sending only for a request with request text, at least one attachment, at least one reference that is ready, or a mix of these. It does not offer sending while an attachment is being prepared or a rejected attachment remains. A reference whose state blocks sending blocks it like a rejected attachment (FR-082). An empty request gets no error message. The system does not send request text longer than the maximum request length [BR-002]. It says that the text is too long, and keeps the text in the request area.
- **Updated at:** 26-10-2026

## Acceptance conditions

### AC-1 · Empty request cannot be sent

- **Given:** A chat with no active request. The request area has no request text, no attachment and no reference.
- **When:** The user tries to send the request.
- **Then:**
  - Nothing is sent. The conversation shows no new user's message.
  - The system shows no error message.
- **Check:** deterministic

### AC-2 · Text alone can be sent

- **Given:** A chat with no active request. The request area holds the request text "a talk on our pilot results" and no attachment.
- **When:** The user sends the request.
- **Then:**
  - The conversation shows "a talk on our pilot results" as the user's message.
- **Check:** deterministic

### AC-3 · Attachment alone can be sent

- **Given:** A chat with no active request. The request area holds one ready attachment "notes.docx" and no request text.
- **When:** The user sends the request.
- **Then:**
  - The conversation shows "notes.docx" as the user's message.
- **Check:** deterministic

### AC-4 · Text of only spaces counts as no text

- **Given:** A chat with no active request. The request text has only spaces and line breaks. The request area has no attachment.
- **When:** The user tries to send the request.
- **Then:**
  - Nothing is sent. The conversation shows no new user's message.
  - The system shows no error message.
- **Check:** deterministic
- **Why:** The use case does not say whether spaces count as request text. This default makes "empty" testable: text of only spaces or line breaks is no text. Trade-off: the user cannot send a message of only spaces, which carries no instruction.

### AC-5 · Attachment being prepared blocks sending

- **Given:** A chat with no active request. The request area holds the request text "a talk from these notes" and the attachment "notes.docx", still being prepared.
- **When:** The user tries to send the request. Then "notes.docx" becomes ready, and the user sends the request again.
- **Then:**
  - The first try sends nothing. The request area is unchanged.
  - The second try sends the request text and "notes.docx" as the user's message.
- **Check:** deterministic

### AC-6 · Rejected attachment blocks sending

- **Given:** A chat with no active request. The request area holds the request text "a talk from these notes", the ready attachment "notes.docx" and a rejected attachment.
- **When:** The user tries to send the request. Then the user removes the rejected attachment and sends the request again.
- **Then:**
  - The first try sends nothing. The request area is unchanged.
  - After the removal, the request text and "notes.docx" are unchanged.
  - The second try sends the request text and "notes.docx" as the user's message.
- **Check:** deterministic

### AC-7 · Request text over the maximum length

- **Given:** A chat with no active request. The request area holds request text one unit longer than the maximum request length [BR-002], and the ready attachment "notes.docx".
- **When:** The user tries to send the request.
- **Then:**
  - Nothing is sent. The conversation shows no new user's message.
  - The request text and "notes.docx" are unchanged in the request area.
- **Check:** deterministic

### AC-8 · The user is told the text is too long

- **Given:** The state after AC-7.
- **When:** The user reads the response of the system.
- **Then:**
  - The response says that the request text is too long.
- **Check:** judged

### AC-9 · Attachments do not count toward the length

- **Given:** A chat with no active request. The request area holds request text exactly as long as the maximum request length [BR-002]. It also holds the ready attachment "report.pdf", whose text is much longer than that length.
- **When:** The user sends the request.
- **Then:**
  - The conversation shows the request text and "report.pdf" as the user's message.
- **Check:** deterministic

### AC-10 · A ready reference alone can be sent

- **Given:** A chat with no active request. The request area holds one reference to a folder in the project folder of the workspace of the chat, in a state that does not block sending, and no request text and no attachment.
- **When:** The user sends the request.
- **Then:**
  - The conversation shows the reference as the user's message.
- **Check:** deterministic

### AC-11 · A blocking reference blocks sending like a rejected attachment

- **Given:** A chat with no active request. The request area holds request text "a talk from these notes" and a reference whose state blocks sending, for example a file that cannot be read [FR-082].
- **When:** The user tries to send the request.
- **Then:**
  - Nothing is sent. The request text and the reference are unchanged in the request area.
- **Check:** deterministic

## Notes

- A file that the system accepted but that has nothing usable is a ready attachment. It does not block sending. FR-009 covers what the system does with it.
- A request in a chat cannot be sent while a request is active in that chat. FR-014 covers it.
- What a reference is, and when its state blocks sending, is covered by FR-082. Naming a reference is not an attachment and adds none [BR-001].
