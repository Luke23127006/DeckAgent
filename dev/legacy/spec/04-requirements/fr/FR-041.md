id: FR-041
title: "Save a provider configuration"
---

## Requirement

- **Statement:** The user can save a new provider configuration, also when others are saved. It connects to a built-in provider or to a custom model API. It gives what the provider needs [BR-006] and a display name. For a custom model API, it also gives a provider ID, a base URL and an API protocol [BR-005]. The system saves the provider configuration and says that it is saved. It keeps every other provider configuration as it was. The user can then add models to it. A new provider configuration of a built-in provider starts with the default models of this release [BR-005]. This holds where that provider has default models. A later release with other default models changes no added model. When the system checks the key at save and the provider refuses it, the system saves no provider configuration. It says that the provider refused the key, and why when the provider gives a reason. It keeps what the user gave, except the refused key.
- **Updated at:** 25-10-2026

## Acceptance conditions

### AC-1 · The provider configuration is saved

- **Given:** No provider configuration is saved. Provider P needs a key [BR-006].
- **When:** The user chooses provider P, gives the key K1 and the display name "Work AI", and saves.
- **Then:**
  - The model setup shows "Work AI" with provider P as saved.
- **Check:** deterministic

### AC-2 · The user is told

- **Given:** No provider configuration is saved. Provider P needs a key [BR-006].
- **When:** The user chooses provider P, gives the key K1 and the display name "Work AI", and saves.
- **Then:**
  - The system says that the provider configuration is saved.
- **Check:** judged

### AC-4 · A custom model API is saved

- **Given:** The state after AC-1. R is an API protocol that a custom model API can use [BR-005].
- **When:** The user chooses to describe a custom model API. The user gives the provider ID "lab", the base URL U1 and the API protocol R. The user also gives the key K2 and the display name "Lab", and saves.
- **Then:**
  - The model setup shows "Lab" with the provider ID "lab" as saved.
  - "Lab" has the base URL U1 and the API protocol R.
  - "Work AI" is still saved with provider P and the key K1.
- **Check:** deterministic

### AC-5 · Another provider is kept apart

- **Given:** The state after AC-1. "Work AI" has the added model M1. Q is another built-in provider.
- **When:** The user adds a provider configuration for Q with the key KQ and the display name "DeepSeek", and saves.
- **Then:**
  - The model setup shows "Work AI" with provider P and "DeepSeek" with provider Q, both as saved.
  - "Work AI" still has the added model M1.
  - "DeepSeek" has no added model that the user gave.
- **Check:** deterministic

### AC-6 · A built-in provider starts with its default models

- **Given:** No provider configuration is saved. In this release, the built-in provider P has the default models D1 and D2 [BR-005]. The built-in provider Q has no default models.
- **When:** The user saves a provider configuration for P, then one for Q.
- **Then:**
  - The added models of the provider configuration for P are D1 and D2.
  - The provider configuration for Q has no added model.
- **Check:** deterministic

### AC-7 · A new release changes no added model

- **Given:** The state after AC-6. The user removed D2 and added the model M1 to the provider configuration for P.
- **When:** The user runs a later release of DeckAgent in which P has the default models D1 and D3.
- **Then:**
  - The added models of the provider configuration for P are D1 and M1.
- **Check:** deterministic

### AC-8 · A key the provider refuses at save

- **Given:** No provider configuration is saved. Provider P needs a key [BR-006]. A test account with P records each request it receives.
- **When:** The user chooses provider P, gives a key the test provider refuses, and saves.
- **Then:**
  - No provider configuration is saved.
  - The response says that the provider refused the key.
  - The display name and the other fields the user gave are still in the setup.
- **Check:** deterministic

## Notes

- Adding models is covered by FR-058. Choosing a model for a chat is covered by FR-055. A setup that lacks something is covered by FR-045. The display name is covered by FR-057. A provider ID that is already saved is covered by FR-061.
- Changing a saved provider configuration is covered by FR-043 and FR-057. Deleting one is covered by FR-063.
- Whether and when a saved key is checked beyond saving goes to the design backlog of the ideal spec, outside `docs/spec/`.
- AC IDs are not renumbered; AC-3 was removed when the provider-ID rule made its case impossible.
