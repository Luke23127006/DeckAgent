---
id: FR-107
title: "Change the design of slides"
---

## Requirement

- **Statement:** When a follow-up request **asks for a design change**, the system **changes the size, the spacing, the position or the layout** of **what the request names** on the **slides in scope**, with a **layout of the template** or a **new one when none fits**, and **takes each colour and font it chooses itself from the theme** of the deck. Each changed slide **keeps its information, figures and meaning**, and the **slide count and order stay** as they were **unless the request asks otherwise**. For a **colour or a font the theme does not hold**, the system **makes the rest of the change** and **asks whether to use it only where the request names it** or to **put it in the theme** of the deck **in place of the theme value whose role it fits best**, **naming that role**, with **both as suggested answers**.
- **Status:** confirmed
- **Why:** DEC-005 and DEC-007: the **model changes the deck source from the template and the theme**, so a **free design change works**, the **deck keeps its design system**, and the **choice of the user wins**.

## Notes

- A request that asks slides **not to follow a rule in words** of the design system is **FR-136**.
- A design change **removes no content to make it fit**; a slide that **does not fit stays unfinished** (FR-092).
- [DEC-007](../../../decisions/DEC-007-how-a-design-system-bounds-the-deck.md): a request is allowed to **ask for another layout** of a slide; a **colour or a font the user asks for is never refused**; one **put in the theme of the deck changes no design system** (a design system is changed in UC-010).
- A colour or a font put in the theme of the deck **takes the place of a theme value with a role**, such as the accent colour; it **never stands beside them with no role**, so the **model always knows what each value of the theme is for**.
