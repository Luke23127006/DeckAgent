## Goal

The user keeps work for different projects in different folders on their computer. They want the chats of each project grouped under a workspace named for it, so they find each chat with its project and reach it again. They also want to start working before having chosen any folder.

## Preconditions

- **Trigger:** The user chooses to add a workspace, to switch the workspace in use, to give a workspace another folder, or to remove one.
- **Preconditions:** DeckAgent runs on the user's computer. The chats, conversations and decks of earlier work are kept [BR-004].

## Interactions

How to read the interactions:

- A **workspace** groups chats for one project folder. The user adds one by choosing a folder. Choosing the same folder again returns the workspace that already uses it.
- Switching the workspace in use among the workspaces that are set up needs no folder. It is part of S1.
- A first start needs no folder: it uses the **default workspace** (Note 1). It has no project folder and cannot be removed.
- A workspace holds the chats that belong to it. Opening an earlier chat of the workspace in use is UC-006. Starting a new chat is UC-012.
- Choosing a folder sets up a workspace for it. The files of the user in that folder are then inside the permission of the chats of the workspace (UC-014) [NFR-003]. The folder holds none of the work DeckAgent saves: the chats, their conversations and their decks stay available without it (Note 6).
- How the system keeps workspaces is not part of this use case.

### Adding and switching workspaces (S1 to S3)

```mermaid
sequenceDiagram
    actor User
    participant DeckAgent
    Note over User,DeckAgent: MF · from the choice of a folder to a workspace
    User->>DeckAgent: S1 · Chooses to add a workspace or to switch the workspace in use
    DeckAgent-->>User: Shows each workspace that is set up, with the workspace in use [FR-071] [FR-072]
    alt Direct switch (at S1)
        User->>DeckAgent: Chooses a workspace that is already set up
        DeckAgent-->>User: Makes that workspace the workspace in use. Asks for no folder again. Changes no file of the user in its project folder. Goes to S3 [FR-071]
        DeckAgent-->>User: Stops no request. A request that is active keeps running in its chat, and its work stays with that chat [FR-054]
    else Adding a workspace (at S1)
        DeckAgent-->>User: Asks the user for a folder on the computer
        User->>DeckAgent: S2 · Chooses a folder on the computer
        alt A1 · Folder already in use by a workspace (at S2)
            DeckAgent-->>User: Makes the workspace that uses the folder the workspace in use. Adds no second workspace. Keeps its display name [FR-071]
        else Folder not yet in use by a workspace (at S2)
            DeckAgent-->>User: Adds a workspace for the folder, with a display name. Makes it the workspace in use [FR-071]
        end
        DeckAgent-->>User: Keeps the files of the user in the folder as they were, and writes no file of its own there. Sends no file of the folder to a model [FR-071] [NFR-003]
        DeckAgent-->>User: Goes to S3
    end
    User->>DeckAgent: S3 · Works in the workspace in use
    DeckAgent-->>User: The chats of the workspace in use are what the user sees as earlier work (UC-006)
    DeckAgent-->>User: Keeps a new chat in the workspace in use (UC-012) [FR-053]
    DeckAgent-->>User: The first start on the computer offers the default workspace, before any folder is chosen [FR-072]
```

### Removing a workspace, changing its folder, and a missing folder (A2 to A6)

```mermaid
sequenceDiagram
    actor User
    participant DeckAgent
    Note over User,DeckAgent: removal, another folder, and what happens when the folder is gone
    opt A2 · Remove a workspace (at S3)
        User->>DeckAgent: Chooses to remove a workspace from the workspaces that are set up
        DeckAgent-->>User: Says what removal does: the workspace is no longer set up and is no longer the workspace in use. It removes nothing else [FR-073]
        DeckAgent-->>User: Says that the folder and every chat of the workspace stay as they are, and that those chats are found among the ungrouped chats [FR-073] [BR-004]
        DeckAgent-->>User: Asks the user to confirm
        alt The user confirms
            DeckAgent-->>User: Removes the workspace. Keeps the folder, its files and every chat of that workspace [FR-073] [BR-004]
            DeckAgent-->>User: Changes no conversation and no deck. The chats of the removed workspace stay reachable among the ungrouped chats [FR-073] [FR-048]
        else The user cancels
            DeckAgent-->>User: Removes no workspace. Keeps every workspace, its project folder and its chats as they were [FR-073]
        end
        note over DeckAgent: The default workspace cannot be removed (FR-072). Returns to S3
    end
    opt A5 · Remove a workspace while a request runs (at S3)
        User->>DeckAgent: Chooses to remove a workspace while a request in one of its chats runs or waits for an answer
        DeckAgent-->>User: Removes no workspace. Says that the request must end before the workspace can be removed [FR-073]
        DeckAgent-->>User: Stops no request, moves no chat and changes no work. The user switches the workspace in use as before [FR-054]
    end
    opt A3 · Project folder missing or unreachable (at S3)
        DeckAgent-->>User: When the project folder of a workspace cannot be read, for example it was moved or access was taken away: says so, and which workspace it belongs to [FR-074]
        DeckAgent-->>User: Says what the user can do, for example put the folder back, give access again, or choose another folder for the workspace (A6) [FR-074] [FR-083]
        DeckAgent-->>User: Keeps every workspace and the saved work of every chat. The chats, their conversations and their decks stay readable without that folder [FR-074] [BR-004]
        note over DeckAgent: The files of the folder cannot be read while it is away, so a request that needs them says what it cannot use (UC-003 A43). Returns to S3
    end
    opt A4 · The project folder is back (at S3)
        DeckAgent-->>User: When the project folder of a workspace can be read again: says that its files can be read again [FR-074]
        DeckAgent-->>User: Reads no chat again and starts no request. The chats were never away
        note over DeckAgent: The chats of the workspace work with the files of the folder again. Returns to S3
    end
    opt A6 · Choose another folder for a workspace (at S3)
        User->>DeckAgent: Chooses another folder for a workspace whose folder moved
        DeckAgent-->>User: Keeps the workspace, its chats, their decks and their history, and makes the chosen folder its project folder [FR-083]
        DeckAgent-->>User: Reads nothing of the folder and sends nothing to a model because of the choice [FR-083]
        alt The folder is the project folder of another workspace
            DeckAgent-->>User: Changes neither workspace. Says which workspace uses that folder, and lets the user switch to it [FR-083]
        else The folder cannot be read
            DeckAgent-->>User: Keeps the earlier project folder of the workspace, and says that the chosen folder cannot be read [FR-083]
        end
        note over DeckAgent: A request that runs or waits for an answer in a chat of the workspace stops the choice: the system says so and changes nothing (A5, FR-083). Returns to S3
    end
```

## Behavior constraints

- Adding, switching and removing workspaces changes no file of the user on the computer. DeckAgent writes no file of its own work into a project folder (Note 6).
- The default workspace is usable at the first start and cannot be removed (Note 1) [FR-072].
- Removing a workspace keeps its chats reachable among the ungrouped chats [BR-004] [FR-073]. The system deletes no chat, conversation or deck when a project folder cannot be read.
- The work DeckAgent saved for a workspace stays available when its project folder is missing, moved, replaced or gone. A file of the folder that a request needs cannot be read while the folder is away (Note 7) [FR-074].
- A project folder chosen for a workspace puts the files of the user in it inside the permission of the chats of that workspace. That permission gives no reach outside the folder, and no change to a file of the user in it (UC-014) [FR-077] [NFR-003].
- No request stops because the user switches the workspace in use, removes a workspace, or loses a project folder [FR-054].

- **Postconditions:**
  - Main flow: the workspace in use is the one the user chose. The files of the user in the project folder are as they were.
  - Direct switch and A1: no second workspace for the folder. The user is asked for no folder again. A request that was active kept running in its chat.
  - A2 confirmed: the workspace is no longer set up. Its chats are found among the ungrouped chats, with their conversations and their decks.
  - A2 cancelled: every workspace is as it was.
  - A3: the workspace stays set up, its chats stay readable, and the user knows what to do.
  - A4: the files of the project folder can be read again.
  - A5: no workspace is removed, and the request keeps running.
  - A6: the workspace keeps its chats and has the chosen folder, or keeps the earlier folder when the choice fails.
- **Minimal guarantee:** Whatever branch fails:
  - No file of the user is changed, moved or deleted. The system deletes no chat, conversation or deck.
  - No request stops because the user adds, switches or removes a workspace, or gives one another folder.

## Notes

1. Folder workspaces are part of the ideal product. The user adds a workspace by choosing one folder; switching needs no folder again; removing a workspace removes no folder, no file, no chat and no history, and its chats stay reachable (A2). A first start needs no folder: it uses the default workspace, which has no folder and cannot be removed.
2. Each workspace other than the default workspace stands for exactly one project folder. No workspace holds two folders, and two workspaces hold no folder in common.
3. The project folder of a workspace is inside the permission of the chats of that workspace. No place outside it is. Naming a workspace is not a full-access permission. What a chat reaches is FR-077 and NFR-003 (UC-014).
4. How the system keeps workspaces, how a workspace names its project folder, and how it keeps the saved work of a workspace apart from that folder, are ADR matters.
5. A chat that was used before workspaces were set up belongs to no added workspace. It stays reachable among the ungrouped chats, as A2 says for the chats of a removed workspace.
6. A project folder holds the files of the user. DeckAgent writes none of its own work there: the conversation, the outline, the deck and the record of each request are kept for the chat, and they stay available when the folder does not. Ordinary work creates, changes and deletes no file of the user in that folder [FR-084]. Only an export the user chooses can put a new file there (UC-004).
7. A project folder that cannot be read takes away the files of the user, not the work of the chats. The chats, their conversations and their decks stay readable (A3). A file of the folder that a request needs cannot be read while the folder is away, and the request says what it cannot use (UC-003 A43). When the folder is gone for good, the system promises no return of a file the user put there, and it claims no copy of one.
8. Switching the workspace in use changes no file of the user and stops no request. A request that is active keeps running in its chat, and its work stays with that chat (S1, FR-054). The switch applies to the work the user starts next.
9. Removing a workspace and giving one another folder both keep the workspace identity and its chats. Neither moves a chat into another workspace, also not into the default workspace. A folder that a workspace still uses returns that workspace (A1, FR-071). A folder added again after its workspace was removed sets up a new workspace, and the chats of the removed one stay among the ungrouped chats (A2, FR-073).
