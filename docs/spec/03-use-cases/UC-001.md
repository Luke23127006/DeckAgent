## Goal

The user has material for a presentation, such as rough ideas, notes, a document or photos. The deck is empty. The user wants a first draft of the slides made for them. They do not want to build the deck slide by slide.

## Preconditions

- **Trigger:** The user starts a request in the request area of a chat that has no deck yet.
- **Preconditions:** The chat has no deck and no slides yet.

## Interactions

How to read the interactions:

- S1 to S3 run the main flow of UC-003 (`includes` UC-003). The request is prepared and sent there, and the system works there. This use case adds what is specific to the first draft. Each other way to enter input is a flow of UC-003 (A2 to A4, and A25).
- The request ends at S3, when the outline is shown and the system waits for the user to confirm it.
- Confirming the outline (S4) sends a new request. S4 to S6 run UC-003 S2 to S4 for it. This use case adds what is specific to the first draft.
- A confirmation given as the answer to a question (A39) stays in the request that asked. It starts no second request.
- In a flow that starts at S4 or S5, "as UC-003 … says" reuses wording only. It does not call UC-003.
- The user reviews the outline and changes it through the conversation (Note 29). A clear typed instruction and a suggested option have the same result.
- The deck uses the default design system. Choosing another one is A5.
- A5 is designed into the product. Which version takes it is a scope decision, not a product-design status.
- A choice to make a presentation or a new deck comes here. The user gives the material, the system asks what is missing before it drafts (A32), and the user confirms the outline before any slide exists (S4, Note 5). It adds no approval step beside the outline.

        DeckAgent-->>User: Adds a section when the new material needs one that the pattern does not have. Drops a section when it does not fit
        DeckAgent-->>User: Says in the message with the outline that it followed the pattern. Names each section it added or dropped

    end
    opt A32 · Ask before drafting the outline (at S3)
        DeckAgent-->>User: When the request and the material leave the topic unknown, or leave open something that would change the outline a lot: asks its questions in the conversation before it drafts [FR-008, FR-020, FR-021]

            User->>DeckAgent: Answers the questions
        end
        DeckAgent-->>User: Drafts the outline from the request, the material and the answers

    end
    opt A33 · Material does not agree with itself (at S3)
        DeckAgent-->>User: Says in the message with the outline which parts do not agree, and where each one is. Chooses neither [FR-011, FR-037]

        note over DeckAgent: Point still open when the user confirms: the slide shows it as unresolved and settles no figure
    end
    opt A34 · Material lacks a needed fact (at S3)
        DeckAgent-->>User: Writes a placeholder instead of a fact the material does not give [BR-?: content and figures added without a source] [FR-010]
        DeckAgent-->>User: Names each missing fact in the message with the outline. Marks each such point in the outline as a placeholder
    end

## Behavior constraints

- The outline is a checkpoint. The system builds no slide until the user confirms the outline (Note 5).
- One chat holds at most one confirmed outline (Note 39). The checkpoint applies to this first draft only.
- Each outline proposal is a response in the conversation. One of them is the **current outline** (Note 30).
- An outline proposal that the system did not finish is not the current outline (Note 39). No flow recovers an unfinished outline.

- **Postconditions:**
  - The chat holds the confirmed outline.
  - The deck has slides made from that outline.
  - The slides use the default design system, or the chosen one when A5 was used.
  - The deck canvas shows the slides.
- **Minimal guarantee:** Whatever branch fails or is interrupted:
  - The request text and attached material are kept. They stay in the conversation if the user sent them, and in the request area if not.
  - Each outline proposal already shown stays in the conversation.
  - Each finished slide stays in the deck.
  - The user does not have to enter anything again.

29. the user changes the outline through the conversation (chat-based outline editing).
   - The user reads the outline, asks for changes, confirms it or cancels it. The user does not edit its titles or points directly.
   - A clear typed instruction can confirm, cancel or revise the outline. A suggested option sends the same instruction, with the same result (UC-003 Note 23).
   - A positive message is not always a confirmation. "Looks good, but add a slide on costs" asks for a change (A23).
   - An unclear message gets a question first, as Note 25 says (Note 32).
   - Confirming (S4) and cancelling (A22) each send a new request. The request that drafted the outline has already ended.
   - A revision changes only what the instruction asks for. A request gives no permission to change content outside its scope.
   - Direct editing of slides is a future capability (UC-007). The deck canvas stays the place to review slides.
30. each outline proposal is a response in the conversation (outline conversation model).
   - The system shows each proposal as its own response. There is no separate place to view or edit the outline.
   - A revision shows a new response (A23). Earlier proposals stay in the conversation as they were.
   - The current outline is the proposal in the latest outline response. A revision starts from it, and a confirmation confirms it.
   - The slides are built from the confirmed outline. An earlier proposal never becomes current by itself.
   - The user can ask for an earlier proposal again (A23). The system presents it again as a new response.
   - That is a revision through the conversation, not an undo or a deck history (UC-008). It promises no exact copy.
   - An unclear reference to an earlier proposal gets a question first (Note 32).
   - Note 5 still holds: one chat holds one outline. Its proposals can show as several responses. Cancelling (A22) removes none of them.
   - How the system keeps proposals is not part of this use case. It is a matter for an ADR.
31. a confirmation of an empty outline gets guidance, not an error (A24).
   - The system confirms nothing and builds no slide.
   - To a typed confirmation, it says briefly that the outline needs content before the slides are built. It suggests asking for a revision.
   - This is a check on the request, not a failure of the work. The system does not say that building the slides failed.
   - "Shows no error message" means no error. It does not mean that the system stays silent.
   - It drafts no new outline by itself and adds no confirmation step.
   - What counts as an empty outline is not decided here.
32. an unclear message about the outline gets a question first.
   - A message about the current outline can leave unclear whether the user wants to confirm, revise or do something else. "OK?" is an example.
   - The system never takes an unclear message as a confirmation.
   - It asks one focused question when the possible meanings lead to results that differ a lot. It does not ask when the context makes the intent clear.
   - It changes no outline and builds no slide before the user answers.
   - The user answers in the conversation or by a suggested option. The answer is part of the same request (UC-003 A38 and Note 22).
   - "Looks good, but add a slide on costs" revises the outline (A23). "Confirm this outline and create the slides" confirms it (S4).
   - These examples show intent. They are not fixed words.
   - This follows minimum necessary clarification (Note 25). An unclear reference to an earlier proposal (Note 30) gets a question in the same way.
   - A39 asks this question since 2026-10-12 (Note 33). UC-003 A38 covers the wait and the answer.
33. a separate flow, A39, asks about an unclear message during the outline review.
   - A32 stays the question before the first outline. A39 asks while the user reviews an outline.
   - A39 covers an unclear confirmation, an unclear revision and an unclear reference to an earlier proposal.
   - The answer goes on as S4, A22 or A23 says, within the same request. It starts no second request.
   - A reply that does not settle the question gets another question when it still matters (UC-003 A38 and Note 24).
   - A39 is the flow that asks. This settles the earlier open question on which flow asks.
34. the system can use general knowledge when it drafts the outline (knowledge use).
   - It can add relevant general knowledge that helps the user's goal. It need not cite each such statement. This needs no web search.
   - It never presents uncertain information as a checked fact.
   - It keeps the meaning of the user's material. It can say a fact in other words or in an equal form, such as "one in four" for 25%.
   - It never adds a fact and says that it comes from the material.
   - It never invents a missing fact about the user's own subject, such as their organization, project or results. A34 applies to such facts.
   - It can make a reasonable inference that does not change the result a lot. It never presents an inference as a fact from the material.
   - An uncertainty that changes the result a lot gets a question first (Note 25).
   - The user asks to use only their material: the system adds no outside factual claim. An attached file alone does not ask for that.
   - Two parts of the material disagree: the system never uses one as settled without telling the user (A33). Open question 2 stays open. Note 39 settles it.
35. images on slides (A42, and UC-002 A12).
   - The agent can use images from the attachments the user gave.
   - The agent can make new images for slides.
   - Not decided: how new images are made, by which model or provider, and whether every model can make them. These stay open for architecture research.
   - The system adds no image service, no image search and no images from the internet. It never changes the selected model and never moves the work to another provider to make an image.
   - A missing capability follows the rules for work that cannot finish (A11, UC-003 A11). Note 38 refines this for a new image the agent chose to add.
   - Using images from attachments approves no file type. The accepted types stay in BR-001.
   - Note 38 says when the system asks about images.
36. the language of the deck.
   - The system writes the outline and the slides in the language the user asks for.
   - When the language is unclear, the rules for clarification apply (Note 25).
   - Vietnamese and English are checked first. This is not a list of languages DeckAgent commits to.
37. reloading or closing the interface (A13). The decision is UC-003 Note 30.
38. choosing a kind of image, and a new image that cannot be made (A42, UC-002 A12).
   - A clear request for attached images, or for new images, is followed. The system asks no question about it.
   - The request does not say, and the choice changes the result a lot: the system asks with suggested options (UC-003 A38). Otherwise it chooses within the request.
   - The system asks no question by default before it builds slides.
   - A new image that the user asked for, or that the result cannot do without, cannot be made: the work cannot finish (A11, UC-003 A11). Finished slides stay. Nothing else takes the place of the image.
   - A new image that the agent chose to add cannot be made: the agent leaves it out and finishes the rest, when the result still meets the request. The closing message says that the image was not made. The system never claims an image it did not make.
   - "Cannot be made" means that no valid way to make the image is available for the request, or that making it fails. A selected model with no image output does not by itself mean that.
   - Reading images, making images and placing an existing image are separate capabilities. How each one works is a matter for architecture research (UC-003 Note 34).
39. the outline, the closing message and an unfinished outline.
   - Before the outline, the topic must be known. The purpose, the audience, the detail, the number of slides and the emphasis count when they are relevant (A32).
   - Missing information gets a question only when it changes the result a lot. The system uses the clarification rules of Note 25 and suggested options.
   - No fixed form, no number of required items and no interface layout is set. An internal checklist is an idea for later design work, not a requirement.
   - Topic still unknown after the user skipped the question: the system makes up no topic and drafts no outline. It asks for the topic again (A32).
   - Two parts of the material disagree: the system says so, chooses neither and keeps the point open (A33). Confirmed with the point open: the slide shows it as unresolved. No figure is made up, and no part is chosen silently.
   - A number of slides that the user asks for is exact. By default, each planned slide gives one slide, in the order of the confirmed outline, with its planned title. An explicit instruction of the user can ask otherwise. The system adds no slide and changes the structure by itself in no other way (S5).
   - A cancelled outline stays in the conversation and is never treated as confirmed. A new request in the chat gets a new outline proposal. The system uses no cancelled proposal by itself (A22).
   - A chat can hold several outline proposals, cancelled ones included. It holds at most one current outline, at most one confirmed outline and one deck. Note 5 holds in this sense. This adds no chat with several decks.
   - The closing message need not name where each figure comes from (S6). The system does not check each figure against other sources. The user checks the figures before using the presentation.
   - The rules against made-up facts, unsupported claims and false claims of checking stay. So does the disclosure of assumptions, placeholders and content not from the material.
   - Tests of the product check that figures keep the meaning of the material.
   - A suggested option that no longer applies runs no outdated action. The system keeps the current state and tells the user (UC-003 S2).
   - An outline proposal that the system did not finish is not the current outline. The system never presents it as a proposal to confirm, and says that the request did not finish. No flow recovers an unfinished outline.
   - A request that ended before any outline was finished: a later request in the chat gets a new outline proposal. The system does not resume the earlier request, and uses no unfinished outline (UC-006 A4).
   - With no language named, the system uses the language of the request text, where it is clear. The language of an attachment does not override a clear request. A language that stays unclear gets the clarification of Note 25.
40. the outline is a detailed content plan, and opening or closing its detail is a viewing action.
   - Each planned slide says what the slide is about and what it argues. It gives the key content, arguments or facts planned for it.
   - A planned slide also holds important figures, placeholders and unresolved points, where they matter.
   - The detail fits the purpose of the slide. No number of points is set.
   - The outline is a content plan, not the final slide. It does not need every final sentence.
   - It holds enough detail for the user to review the plan. The user can find content that is missing, incorrect or poorly organized before the slides are built.
   - The system shows the outline as a concise overview of the planned slides. The user can read the detail of one planned slide or of all planned slides, and hide it again.
   - These are viewing actions: they change no outline, confirm nothing and send no request. The confirmed outline keeps the same detail and stays read-only.
