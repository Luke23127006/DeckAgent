## Situation and goal

- The user has material for a presentation, such as rough ideas, notes, a document or photos. The deck is empty.
- The user wants a first draft of the slides made for them. They do not want to build the deck slide by slide.

## Trigger and preconditions

- **Trigger:** The user starts a request in the request area of a chat that has no deck yet.
- **Preconditions:** The chat has no deck and no slides yet.
- **Evidence:** [observed: claude-report (a new request starts with an empty presentation)] [observed: napkin-report (a separate step for creating a presentation)]

## Main flow

- The main flow takes the user's input without saying how the user entered it. UC-003 S1 takes the request text. Each other way to enter input is an alternative flow of UC-003 (A2 to A4, and A25).
- S1 to S3 call UC-003. The request is prepared and sent there, and the system works there. This use case adds what is specific to the first draft.
- The request ends at S3, when the outline is shown and the system waits for the user to confirm it.
- Confirming the outline (S4) sends a new request. S4 to S6 call UC-003 S2 to S4 for it. This use case adds what is specific to the first draft.
- A confirmation given as the answer to a question (A39) stays in the request that asked. It starts no second request.
- In a flow that starts at S4 or S5, "as UC-003 … says" and "as in UC-003 …" reuse wording only. They do not call UC-003.
- The user reviews the outline and changes it through the conversation (Note 29). A clear typed instruction and a suggested option have the same result.
- The deck uses the default design system. Choosing another one is A5.
- The outline is a checkpoint. The system builds no slide until the user confirms the outline.
- One chat holds one outline. The checkpoint applies to this first draft only.
- Each outline proposal is a response in the conversation. One of them is the **current outline** (Note 30).

### S1 · Provide the material

- **User:** Provides the material and instructions for the deck in the request area.
- **System:**
  - Shows what the user provided in the request area, as UC-003 S1 says.
- **Reqs:** none
- **Updated at:** 10-10-2026

### S2 · Send the request

- **User:** Sends the request.
- **System:**
  - Sends the request as UC-003 S2 says.
- **Reqs:** none
- **Updated at:** 10-10-2026

### S3 · Wait for the outline

- **User:** Waits for the outline.
- **System:**
  - Shows the status message as UC-003 S3 says.
  - Shows the proposed **outline** in the conversation, as its response. It is the current outline.
  - Offers to confirm or cancel the outline as suggested options.
  - Lets the user ask for changes to the outline in a new request. The user does not edit the outline directly.
  - Says that the system builds no slide until the user confirms.
  - Does not show the deck canvas yet.
  - Ends the request as UC-003 S4 says, once the outline is shown.
- **Reqs:** FR-001, FR-003, FR-004, FR-005, FR-008
- **Evidence:** [observed: napkin-report (outline: proposes an outline and waits for approval)] [assumed: confirm and cancel offered as suggested options]
- **Updated at:** 12-10-2026

### S4 · Confirm the outline

- **User:** Reviews the current outline and confirms it.
- **System:**
  - Sends the confirmation as a new request, as UC-003 S2 says. An answer to a question in A39 stays in that request.
  - Confirms the current outline. Never confirms an earlier proposal in its place.
  - Shows that the outline is confirmed. The **confirmed outline** is read-only.
  - Shows that it is preparing the slides from the confirmed outline.
- **Reqs:** FR-003
- **Updated at:** 12-10-2026

### S5 · Watch the deck build

- **User:** Waits and watches the deck canvas.
- **System:**
  - Shows the **deck canvas**. The deck canvas shows that work is in progress.
  - Shows each slide as soon as it is done. The system builds each slide from the confirmed outline, in the default design system [BR-003] [NFR-002].
  - Shows in the deck canvas which slides are done and which are still to come.
  - Does not change which slide the user is looking at.
  - Shows the **status message** as UC-003 S3 says.
  - Does not offer adding slides by hand meanwhile.
- **Reqs:** FR-022, FR-023
- **Evidence:** [observed: claude-report (waiting display; how slides arrive: the view stays on the first slide)] [observed: napkin-report (layout step and the editor: the view moves to each new slide by itself, not adopted)]
- **Updated at:** 12-10-2026

### S6 · Review the draft

- **User:** Reviews the draft.
- **System:**
  - Shows the full draft deck in the deck canvas.
  - Shows that its work is done and lets the user send a new request, as UC-003 S4 says.
  - Shows a closing message that says the draft is ready.
  - The message tells what was made per slide, which assumptions were used, and which text is placeholder.
  - The message also tells which content did not come from the user's material [BR-?: disclosure of content not from the user's material] and what the system did not check.
  - For each figure taken from the user's material, the message names the part it comes from [BR-?: how a source is named].
  - The message says that naming a source does not mean the system checked the claim.
- **Reqs:** FR-023, FR-024
- **Evidence:** [observed: claude-report (closing message: what was made, assumptions, placeholders, what was not checked)] [observed: napkin-report (closing message: one question and buttons, no summary)] [observed: claude-report (a closing message said that a citation came from memory and not from a lookup)] [assumed: naming the source of each figure]
- **Updated at:** 12-10-2026

### A30 · Draft the outline from a pattern

- **End:** Continues at S4

### A32 · Ask before drafting the outline

- **At:** S3
- **End:** Same step
- **When:** The request and the material leave the topic unknown. Or they leave open something that would change the outline a lot [BR-?: when the system asks before the outline]. Examples are the audience, the purpose or the length.
- **System:**
  - Asks its questions in the conversation before it drafts the outline. It asks nothing that the request or the material already answers.
  - Offers answers to choose from for each question. Lets the user give their own answer.
  - Lets the user skip a question.
  - Keeps the request open while it waits, as UC-003 A38 says. The answers are part of the same request.
  - Drafts the outline from the request, the material and the answers.
  - Skipped question: says in the message with the outline what it assumed instead.
- **Reqs:** FR-008, FR-020, FR-021
- **Evidence:** [observed: claude-report (a vague one-line request got questions with answers to choose from before any slide)] [observed: napkin-report (a picture with no text got questions on topic, audience, purpose and length before the outline; a full request got none)] [observed: claude-report (an own answer and a skip were offered; neither was tried)] [assumed: what the system does after a skip]
- **Updated at:** 12-10-2026

### A33 · Material does not agree with itself

- **At:** S3

- **System:**

  - Does not say which part is right.
  - Marks the point in the outline as open, so the user decides at S4.

### A23 · Send a new instruction for the outline

- **At:** S4
- **End:** Returns to S3
- **When:** The user sends an instruction to change the current outline, or to use an earlier proposal again. Examples are a request to add a point, or to go back to the first proposal.
- **System:**
  - Sends the instruction as a new request, as UC-003 S2 says. An answer to a question in A39 stays in that request.
  - Revises the current outline to follow the instruction.
  - Keeps each part of the current outline that the instruction does not ask to change.
  - Earlier proposal asked for: presents that proposal again. It is not an exact restore (Note 30).
  - Shows the result as a new response in the conversation. It becomes the current outline.
  - Keeps each earlier proposal in the conversation as it was.
  - Builds no slide.
- **Reqs:** FR-001, FR-005, FR-012

## Postconditions and minimal guarantee

Proposals, to be confirmed against recordings.

- **Postconditions:**
  - The chat holds the confirmed outline.
  - The deck has slides made from that outline.
  - The slides use the default design system, or the chosen one when A5 was used.
  - The deck canvas shows the slides.
- **Minimal guarantee:** Whatever branch fails or is interrupted:
  - The request text and attached material are kept. They stay in the conversation if the user sent them, and in the request area if not.
  - Each outline proposal already shown stays in the conversation.
  - Each finished slide stays in the deck.
  - The user does not have to enter anything again.

29. Design decision (owner, 2026-10-12): the user changes the outline through the conversation (chat-based outline editing).
   - The user reads the outline, asks for changes, confirms it or cancels it. The user does not edit its titles or points directly.
   - A clear typed instruction can confirm, cancel or revise the outline. A suggested option sends the same instruction, with the same result (UC-003 Note 23).
   - A positive message is not always a confirmation. "Looks good, but add a slide on costs" asks for a change (A23).
   - An unclear message gets a question first, as Note 25 says (Note 32).
   - Confirming (S4) and cancelling (A22) each send a new request. The request that drafted the outline has already ended.
   - A revision changes only what the instruction asks for. A request gives no permission to change content outside its scope.
   - Considered: editing the outline text directly. Not selected for V1.
   - Why: the system revises the outline from the user's intent. The user does not have to fit related changes together by hand.
   - Direct editing of slides is a future capability (UC-007). The deck canvas stays the place to review slides.
   - S3, S4, S5, A12, A22, A23 and A24 follow this note since 2026-10-12. Until then, S3 let the user edit the outline text. This note selects no flow.
30. Design decision (owner, 2026-10-12): each outline proposal is a response in the conversation (outline conversation model).
   - The system shows each proposal as its own response. There is no separate place to view or edit the outline.
   - A revision shows a new response (A23). Earlier proposals stay in the conversation as they were.
   - The current outline is the proposal in the latest outline response. A revision starts from it, and a confirmation confirms it.
   - The slides are built from the confirmed outline. An earlier proposal never becomes current by itself.
   - The user can ask for an earlier proposal again (A23). The system presents it again as a new response.

   - Considered: one outline that each revision changes in place. Not selected.

34. Design decision (owner, 2026-10-12): the system can use general knowledge when it drafts the outline (knowledge use).
   - It can add relevant general knowledge that helps the user's goal. It need not cite each such statement in V1. This needs no web search.
   - It never presents uncertain information as a checked fact.
   - It keeps the meaning of the user's material. It can say a fact in other words or in an equal form, such as "one in four" for 25%.
   - It never adds a fact and says that it comes from the material.
   - It never invents a missing fact about the user's own subject, such as their organization, project or results. A34 applies to such facts.
   - It can make a reasonable inference that does not change the result a lot. It never presents an inference as a fact from the material.
   - An uncertainty that changes the result a lot gets a question first (Note 25).
   - The user asks to use only their material: the system adds no outside factual claim. An attached file alone does not ask for that.
   - Two parts of the material disagree: the system never uses one as settled without telling the user (A33). Open question 2 stays open.
   - Considered: not recorded.
   - Why: general knowledge helps make a useful deck. An invented fact about the user's own subject cannot be trusted.
