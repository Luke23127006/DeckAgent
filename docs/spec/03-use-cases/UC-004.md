## Goal

The user has a deck they are happy with and wants it as a file they can keep, send, print or present, or a file that looks the same on any device, or a file to change in their own tools. The deck in the chat stays as it is.

## Preconditions

- **Trigger:** The user chooses to get the deck as a file.
- **Preconditions:** The chat has a deck with at least one slide.
- **Evidence:** [observed: napkin-report (after the deck was built, the product offered to export it as a next step)]

## Active interactions

Every flow below is Active in the ideal product; this use case records no Closed flow. Nothing here says which version takes a flow. The flow ID A4 is retired and never reused (Note 8).

How to read the interactions:

- The user gets the deck as an editable file or as a fixed file. The export changes the form of the deck. It never changes the content of a slide.
- Presenting is done in the user's own tools, from the file.
- Exporting the conversation and the session archive of the chat is UC-016. That export and this one are different abilities, and neither replaces the other.

## Behavior constraints

- The deck in the chat is never changed by an export; whatever fails or is interrupted, the user can choose the export again.
- Presenter notes stay out of the file by default (Note 7). Notes come from a first draft (UC-001 A37) or a change request (UC-002 A9).

Proposals, to be confirmed against recordings.

- **Postconditions:**
  - The user has a file of the kind they chose.
  - The file holds every slide of the deck, as the deck was when the export started.
  - The file holds no presenter notes unless the user chose to put them in.
  - The conversation says how many slides the file holds and what was not kept.
- **Minimal guarantee:** Whatever branch fails or is interrupted:
  - The deck in the chat is exactly as it was before the export.
  - The user can choose the export again.

## Notes

1. Design decision (owner, 2026-10-09): the user gets the deck as an editable file or as a fixed file. The product does not import an existing deck file as a deck it can change, and does not edit such a file. It does allow a basic edit of a deck it made, on the deck canvas. That edit is UC-007. The editable file lets the user go further in their own tools. The file types are a business rule [BR-?: export formats]. Since 2026-10-13, a deck file can be an attachment of a request, whoever made it (owner, 2026-10-13) [BR-001]. The system reads it as material for the request. It is not imported as slides the user can change, and the file itself is not changed. Until 2026-10-13, this note said that the product does not read other people's deck files.
2. The export changes the form of the deck, never its content. A change to the content is a request to the system or an edit on the deck canvas. An example is a request to make the deck denser for reading. The export includes every such change.
3. Design decision (owner, 2026-10-09): the product has no way to present the deck. The user presents from the file, in their own tools.
4. The user prints the fixed file. Whether slides print well without colour is a property of the slides and not of the export [NFR-?: readable without colour].
5. This draft assumes the export uses no model and offers no way to stop it. The export is short.
6. Design decision (owner, 2026-10-09): the product has no shared viewing of a deck. The user sends the file. The file leaves the product at S3, so the product cannot control who reads it.
7. Design decision (owner, 2026-10-09): presenter notes stay out of the file by default (A2). The user can choose to put them in. The kinds of file that can hold notes are a business rule. Notes come from a first draft (UC-001 A37) or a change request (UC-002 A9).
8. The export writes a file on the user's computer and needs no network. The ID A4 is retired. IDs are never renumbered.
