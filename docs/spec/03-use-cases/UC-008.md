## Goal

The user changed the deck, by a request or by hand, and likes the result less than before. They want to see how the deck was earlier and what changed since then, and they want that earlier deck back, without rebuilding it and without starting a new chat.

## Preconditions

- **Trigger:** The user asks to see the earlier states of the deck.
- **Preconditions:** The chat has a deck. The system is not working on a request in this chat.
- **Evidence:** [assumed]

## Active interactions

Every flow below is Active in the ideal product; this use case records no Closed flow. Nothing here says which version takes a flow.

How to read the interactions:

- A state is the deck as it was at one moment. Every state belongs to the same deck in the same chat. A state is not a variant (UC-011); a variant is another deck beside this one.
- The main flow looks at one earlier state and makes it the current deck. When the system keeps a state is open (Decisions needed). How it keeps a state is not part of this use case.
- A finished request is not undone; only the earlier states of the deck are (Note 5).

## Behavior constraints

- Looking at a state changes nothing in the current deck. A branch that fails or is left changes nothing in the current deck or in the other states.
- This use case makes no second deck (Note 1); a separate deck for another use is UC-011.

Proposals, to be confirmed against recordings.

- **Postconditions:**
  - Main flow: the current deck is the chosen earlier state.
  - A2 and A3: the current deck is as it was.
  - The conversation keeps every message.
- **Minimal guarantee:** Whatever branch fails or is left:
  - Looking at a state changes nothing in the current deck.
  - A branch that fails or is left changes nothing in the current deck or in the other states.

## Decisions needed

1. S1: when does the system keep a state? After each request (UC-002), after each change by hand (UC-007), or when the user chooses to keep one? Owner to decide.
2. S3: after going back, are the newer states still there? Can the user go forward to them again? Owner to decide.
3. S2: can the user look at a state without going back to it? This draft says yes. Owner to confirm.
4. S1: are the states still there after DeckAgent is closed and the chat is opened again (UC-006)? Owner to decide.
5. S1: does a request that stopped or failed leave a state? This links to the later try-again action (UC-002 Decisions needed 1 to 3, UC-003 Note 18). Owner to decide.
6. S3: does going back change what the model knows at the next request? Owner to decide.
7. S3: what does the user see when going back fails partway? This use case states no rule for it. Owner to decide.

## Notes

1. A state and a variant are not the same. A state is the same deck at an earlier moment. A variant is another deck that exists beside it. This use case makes no second deck.
2. This use case is not UC-006. UC-006 opens an earlier chat. This use case stays in the current chat and changes which state is its deck.
3. Undo in UC-007 (A5) takes back the last change by hand. This use case chooses among earlier states. Whether the two are one behavior is open (UC-007 open questions).
4. Design choice for an ADR proposal: this use case needs the system to keep earlier states of a deck. How it keeps them (checkpoints, copies, a database or files) is an ADR matter.
5. Design decision (owner, 2026-10-11, revised the same day): a finished request is not undone.
   - Earlier decision: after a request finished, the user could bring back the deck as it was before it (undo of the last request, R1). The owner approved it once. A separate use case was drafted for it and removed before it was committed.
   - Revised decision: a finished request makes its result the current deck. The product has no undo or rollback of a request. The user who dislikes the result sends a follow-up request (UC-002). That request uses the current deck as context.
   - Why: the work focuses on stopping a request, keeping finished work, and refining the deck through new requests.
   - Considered: undo of the last request (R1), no version assigned; a full deck history (R2, this use case), a future candidate. The open questions on several undos, redo and a new request after an undo left with R1.
   - This use case keeps its deck history flows. Neither decision takes them. This note takes no flow.
   - Undo in UC-007 A5 takes back a change by hand (Note 3). The later try-again, continue and edit-the-request actions concern a request that did not finish (UC-003 Note 18). Both differ from undo of a request.
