## Situation and goal

- The user wants DeckAgent to make decks with models they choose.
- The user has accounts with one or more model providers, and a key for each account. Or the user has a model service of their own.
- The user has no model ready yet, or wants more models or another provider. Or a key they gave no longer works.
- The user wants the models ready without losing the request they were preparing.

## Trigger and preconditions

- **Trigger:** The user chooses to set up models. Examples: from the request area (UC-003 A28), or at the first start. Also after a request found no selectable model (UC-003 A17).
- **Preconditions:** DeckAgent runs on the user's computer. A request can be active in a chat while the model setup is open (A12).
- **Evidence:** [observed: owner report (the option to add or change models opens the model setup dashboard); not recorded] [assumed: the first start as a trigger]

## Main flow

- The main flow saves a new provider configuration and adds models to it. The user can save several provider configurations, one at a time.
- A provider configuration connects to a built-in provider or to a custom model API (S2, S3). Each provider ID has at most one saved provider configuration [BR-008].
- The provider ID of a saved provider configuration never changes. To use another provider, the user adds a provider configuration.
- The user then chooses among the selectable models for a chat (UC-003 A27). Choosing a model for a chat is not part of this use case.
- The key belongs to the user's own account with the provider (Vision P-1).
- How and where the system keeps the key is not part of this use case.
- S6 is new on 12-10-2026. It comes before S5. Step IDs are never renumbered.

### S1 · Open the model setup

- **User:** Chooses to set up models.
- **System:**
  - Opens the model setup **dashboard**.
  - Shows each saved provider configuration with its display name, its provider ID and its added models. Or says that none is saved.
  - Shows only whether each saved provider configuration has a saved key. Shows no part of the key.
  - Lets the user add a provider configuration, also when others are saved.
  - Lets the user change or delete a saved provider configuration.
  - Lets the user add, remove or restore the models of a saved provider configuration.
  - Keeps the conversation, the request text and the attachments as they were.
- **Reqs:** FR-038, FR-039, FR-040, FR-041
- **Evidence:** [observed: owner report (the option to add or change models opens the model setup dashboard; the request text and files stay); not recorded] [assumed: what the dashboard shows]
- **Updated at:** 13-10-2026

### S2 · Choose a provider

- **User:** Chooses a built-in provider for the new provider configuration, or chooses to describe a custom model API.
- **System:**
  - Shows the **built-in providers** the user can choose [BR-005]. Offers none that a saved provider configuration already uses [BR-008].
  - Lets the user describe a **custom model API** instead. Shows the API protocols it can use [BR-005].
  - Says what the provider needs before its models can run, such as a key [BR-006].
  - Says that a key comes from the user's own account with the provider.
  - Says that each request run through this provider configuration goes to this provider.
- **Reqs:** FR-039, FR-061
- **Evidence:** [assumed]
- **Updated at:** 12-10-2026

### S3 · Give the connection details and a name

- **User:** Gives what the provider needs, such as the key of their account, and a display name.
- **System:**
  - Built-in provider: uses its provider ID. Uses its default settings for each one the user does not change [BR-006].
  - Custom model API: takes the provider ID, the base URL and the API protocol the user gives [BR-005] [BR-006].
  - Lets two custom model APIs use the same API protocol.
  - Takes the key or other authentication information, when the provider needs it [BR-006].
  - Shows no part of the key again after the user saves it.
  - Never shows the key in the conversation.
  - Keeps the display name as the user gave it. Never uses it to set the provider ID.
- **Reqs:** FR-040, FR-041, FR-057, FR-061
- **Evidence:** [assumed]
- **Updated at:** 13-10-2026

### S4 · Save the setup

- **User:** Saves the setup.
- **System:**
  - Saves the provider configuration with its provider ID, its display name and what the provider needs.
  - Keeps the provider ID as saved. It never changes later.
  - Built-in provider with default models: gives the new provider configuration its default models of this release [BR-005].
  - Keeps every other saved provider configuration as it was.
  - Says that the provider configuration is saved.
- **Reqs:** FR-041, FR-061
- **Evidence:** [assumed]
- **Updated at:** 13-10-2026

### S6 · Add models

- **User:** Chooses the models to add to the provider configuration, and saves them.
- **System:**
  - Gets the **model catalog** from the provider when the user asks for it. Shows the models it returns.
  - Changes no added model and no selected model when it gets the model catalog. Runs no model for it.
  - Lets the user choose models from the model catalog. Adds none that the user did not choose.
  - Lets the user give a **model ID** by hand, also one that the model catalog does not hold [BR-005].
  - Saves each chosen model as an **added model** of this provider configuration only.
  - Does not ask the provider to run a model before saving it.
  - Says which models were added.
- **Reqs:** FR-058
- **Evidence:** [assumed]
- **Updated at:** 12-10-2026

### S5 · Go back to the chat

- **User:** Goes back to the chat.
- **System:**
  - Shows the conversation, the request text and the attachments as they were.
  - Lets the user choose among the **selectable models** of every provider configuration [BR-005].
  - Selected model of this chat removed: shows that the chat has no selected model, as UC-003 A41 says.
- **Reqs:** FR-038, FR-055, FR-065
- **Evidence:** [observed: owner report (the user chooses among the models that are set up; the chat then uses the chosen model); not recorded]
- **Updated at:** 12-10-2026

## Alternative flows

### A1 · Change a provider configuration

- **At:** S1
- **End:** Returns to S1
- **When:** The user changes a saved provider configuration [BR-006]. The change is to the key or other authentication information, or to the display name. Or it is to the base URL, where the provider allows it. The user then saves. A request can be active, also one that waits for the user's answer. An example is a key the provider refused (UC-003 A18).
- **System:**
  - Replaces what the user changed. Keeps the rest, and adds no second provider configuration.
  - Keeps the provider ID. To use another provider, the user adds a provider configuration (S2).
  - Shows no part of the old key or of the new key.
  - Keeps its added models and the selected model of each chat. Checks none of them with the provider.
  - New display name: names the group of its models with it. Changes no provider ID, key, added model or selected model.
  - Uses what was saved for each request that starts later. An active request keeps the settings it started with.
  - Says what was changed. Stops, restarts and sends again no request.
- **Reqs:** FR-040, FR-042, FR-043, FR-057, FR-061
- **Evidence:** [assumed]
- **Updated at:** 13-10-2026

### A2 · Remove an added model

- **At:** S1
- **End:** Returns to S1
- **When:** The user removes an added model from a provider configuration, and saves.
- **System:**
  - Removes the model from the added models of this provider configuration only.
  - Deletes and changes nothing at the provider.
  - Keeps the provider configuration and its other added models.
  - The model is no longer selectable in any chat.
  - A chat that selected it has no selected model, as UC-003 A41 says. Selects no other model.
  - Changes no conversation, request, attachment or deck.
  - Adding the model again later makes it selectable. It becomes the selected model of no chat by itself.
- **Reqs:** FR-059
- **Evidence:** [assumed]
- **Updated at:** 12-10-2026

  - Keeps every change the user saved, also one saved earlier in this setup.
  - Adds no provider configuration that the user did not save.
  - Shows the conversation, the request text and the attachments as they were.
  - Selected model of the chat removed: shows that the chat has no selected model, as UC-003 A41 says.

## Postconditions and minimal guarantee

Proposals, to be confirmed against recordings.

- **Postconditions:**
  - Main flow: a provider configuration is saved with its provider ID, its display name and its added models. The user can choose among them for a chat. Saving shows neither that the provider accepts the key nor that it runs a model.
  - A1: later requests through the provider configuration use what the user changed. Its provider ID and its added models stay.
  - A2: the model is no longer among the selectable models. Nothing changed at the provider.
  - A8: the provider configuration has the models the user added.
  - A11: the provider configuration and its added models are no longer in DeckAgent. Every chat and deck is as it was.
  - A13: confirmed, the added models are exactly the default models. Cancelled, the added models are as they were.
  - The conversation, the request text and the attachments are as they were.
- **Minimal guarantee:** Whatever branch fails or is left:
  - What the user saved stays as saved. Exceptions are a model the user removed (A2) and a provider configuration the user deleted (A11).
  - No provider ID changes. A provider configuration that an active request uses is never deleted (A12).
  - A failed request to the provider removes no provider configuration and no added model (UC-003 A18).
  - Getting the model catalog changes no added model (S6, A7).
  - The key is never shown in the conversation.
  - The conversation, the request text and the attachments are as they were.

## Open questions

1. A6: does the system check a key when the user saves it, or only when a request runs (UC-003 A18)? Owner to decide.
2. Settled (owner, 2026-10-13): V1 promises no model that runs on the user's computer. Such a model service can work as a custom model API, but V1 neither tests nor promises it (Note 14).
3. S2, S3: what does each built-in provider need besides a key? Which of its default settings can the user change [BR-006]? Its base URL can change only where the provider allows it (Note 13). Each answer waits for checks with the provider. Owner to decide.
4. S2, S3: which API protocols can a custom model API use [BR-005]? The answer waits for technical research. Owner to decide. Which built-in providers are offered was settled on 2026-10-12 (Note 13).
5. Settled (owner, 2026-10-13): with no model, the system guides the user to the model setup. Opening it by itself is not required (Note 14).
6. Settled (owner, 2026-10-13): a new provider configuration of a built-in provider starts with its default models, where they exist (S4, Note 14).
7. Settled (owner, 2026-10-13): a name of whitespace only is empty. Capital letters and outer whitespace do not make two names different (A10, Note 14) [BR-008].
8. Settled (owner, 2026-10-13): no. The provider IDs of built-in providers stay reserved (A9, Note 14) [BR-008].
9. S3: how does the system know that a custom model API needs a key? Can the user change its API protocol after saving [BR-006]? Owner to decide.

## Notes

1. This use case changes the saved provider configurations and their added models. Choosing a model for a chat or a request is UC-003 A27. One use case, not two: adding, changing, removing, restoring and deleting share the goal of ready models.
2. A refused key or a refused model ends the request (UC-003 A18). A18 does not go to this use case. The user can also choose another selectable model instead (UC-003 A27). The user can change the provider configuration here (A1), then send a new request.
3. UC-003 A17 and A28 go to this use case. A17 brings a request that found no selectable model. A28 brings a user who chose to set up models.
4. How and where the system keeps the key is an ADR matter. The proposed boundary B-3 in the vision is related.
5. A provider usage limit is a property of the user's provider account (Vision P-1). This use case shows no limit and no price.
6. When a model fails, the system does not move to another model by itself. It ends the request and keeps the selected model (UC-003 A11, A18, Note 27; FR-019). This use case does not change that behavior. Until 2026-10-12, this note said it was not decided.
7. Design decision (owner, 2026-10-11): the user sets up a model with their own key inside DeckAgent. No developer prepares the model for them. Considered: a model set up outside the user's own steps, not selected. Why: the user brings their own key (Vision P-1). The owner wants users to finish the setup without a developer's help. Which providers and models are offered stays open (open question 4). This note selects no flow.
8. Design decision (owner, 2026-10-11, revised the same day): minimum model setup. Replaced in part by Note 9 (owner, 2026-10-12). V1 has one provider configuration, and the user chooses among its available models. One model no longer runs every V1 request.
   - Earlier direction: one model set up at a time, which the user could replace.
   - Revised decision: V1 needs only one working model, set up with the user's own key. That model runs every request of the journey: generate, preview and refine.
   - Why: the core outcomes come before a wider management of models.
   - Future candidates, with no version assigned: several saved models, switching between them, replacing a model, and a model per request.
   - The behavioral model stays open to several models and providers (Vision P-1). Since 2026-10-12, S4, S6 and S5 say three things. Provider configurations are saved, models are added to them, and selectable models can be chosen. This note selects no flow.
9. Design decision (owner, 2026-10-12): one provider configuration, with all its available models. Replaces in part Note 8. Replaced in part by Note 10 (owner, the same day). V1 has several provider configurations, and the user adds their models.
   - A provider configuration is one saved connection to a model provider. It holds a display name, the user's key and what the system needs to reach the provider.
   - The display name is the user's own text. It never says which provider the provider configuration connects to. The system does not rename it.
   - Example: the display name is "DeepSeek". The provider configuration connects to Gemini with a Gemini key. The name stays "DeepSeek".
   - The available models of a provider configuration come from the provider it connects to. They never come from its display name.
   - The user chooses the selected model among the available models. One model is selected at a time. It belongs to the provider configuration that gives access to it.
   - The models the user can choose from are grouped by provider configuration. Each group is named by the display name of its provider configuration.
   - V1 has one provider configuration at a time, so the user sees one group. A later version can allow several, and so several groups. The grouping stays the same.
   - V1 has one provider configuration. It is one slot, not a fixed provider. The limit was the value of a business rule, retired on 12-10-2026 (Note 10).
   - The user can replace the key and change the display name. A saved key replaces the earlier key. It adds no second provider configuration.
   - Leaving the model setup without saving applies no unsaved change. It does not undo a change already saved. Replacing the key does not send a failed request again.
   - Future candidates, with no version assigned: a second provider configuration, and several with their own keys. Also choosing among them and removing one.
   - Open then: how the provider is set, and which models count as available models. Note 10 settles both. How a selected model works is UC-003 Note 25 (owner, 2026-10-12).
   - Why: the owner wants to test different providers through one provider configuration. This note selects no flow.
10. Design decision (owner, 2026-10-12): several provider configurations, and models the user adds. Replaces in part Notes 8 and 9. Replaced in part by Note 11 (owner, the same day). A provider configuration keeps its provider ID, so its provider never changes.
   - The user can save several provider configurations. Two can connect to the same provider with different keys. No number of them is set.
   - The user can change the provider, the key and the display name of a saved provider configuration (A1). A change of provider keeps the display name.
   - The model catalog and the added models are different. The user chooses which models to add, from the model catalog or by model ID (S6).
   - A model ID is saved without a check with the provider. A provider that refuses it at a request ends that request (UC-003 A18). The added model and the provider configuration stay.
   - A missing model catalog leaves adding by model ID possible (A7). It is not a failed request, and it makes no added model unselectable.
   - A change of provider keeps the models added for the earlier provider, but they are not selectable. The system gives no model ID to another provider by itself.
   - The user can remove an added model (A2). Removing it changes nothing at the provider. A chat that selected it chooses again (UC-003 A40).
   - In V1 the model setup is the Models part of the settings (`../00-current-scope/VERSIONS.md`).
   - Considered: one provider configuration (Note 9), and every model a key can use as an available model. Neither is kept.
   - Open then: a change back to an earlier provider, and a change of address. Also removing a whole provider configuration, and display names. Note 11 settles them.
   - Why: not recorded. A1, A2, A7 and A8 follow this note since 2026-10-12. Only `versions` selects flows.
11. Design decision (owner, 2026-10-12): model provider management. Replaces in part Note 10.
   - A provider configuration is a saved connection to a model service, not only a key. It connects to a built-in provider or to a custom model API.
   - A custom model API has a provider ID, a base URL, an API protocol and, when needed, a key [BR-006]. Two can use the same API protocol.
   - Each provider ID has at most one saved provider configuration [BR-008]. A built-in provider can be added again after its provider configuration is deleted.
   - The provider ID never changes after saving. The user can change the key, the base URL and the display name (A1). To use another provider, the user adds a provider configuration.
   - The display name is not empty, and no other saved provider configuration has it (A10). It never sets the provider ID.
   - Getting the model catalog adds no model and changes no selection (S6). When it fails, adding a model ID by hand stays possible (A7).
   - Restoring the default models needs the user's confirmation first (A13). Cancelling changes nothing.
   - Deleting a provider configuration removes it and its added models from DeckAgent only (A11). Chats and decks stay. No chat gets another model by itself.
   - The user cannot delete a provider configuration that an active request uses, also one that waits for an answer (A12). The request is not stopped for it.
   - Superseded: a change of provider, models kept from an earlier provider, and two provider configurations for one provider (Note 10). The requirement for a change of provider is retired.
   - In V1 the model setup holds built-in providers, custom model APIs, the model catalog and the saved provider configurations (`../00-current-scope/VERSIONS.md`). The owner chose this organization from a reference product. It fixes no interface design (UCG-13).
   - Why: not recorded. A1, A2 and A7 to A13 follow this note since 2026-10-12. Only `versions` selects flows.
12. Design decision (owner, 2026-10-12): adding a provider, active requests, restoring default models and removed models. Adds to Note 11.
   - S2 offers only built-in providers that no saved provider configuration uses. A saved one stays open to change (A1).
   - The provider ID is still checked when the user saves (A9). This holds also for a custom model API.

13. Design decision (owner, 2026-10-12): built-in providers, base URLs and default models. Adds to Notes 11 and 12.

14. Design decisions (owner, 2026-10-13): first setup, default models, provider IDs, display names, keys and local models.
   - With no selectable model, the system guides the user to the model setup (UC-003 A17). It need not open the model setup by itself.
   - A new provider configuration of a built-in provider starts with the default models DeckAgent sets for that release, where it has them (S4) [BR-005]. Their model IDs are still open.
   - The default models of a built-in provider can change between releases. A release never replaces, removes or changes a model the user added. Restoring the default models stays as A13 says.
   - The provider IDs of built-in providers are stable. They stay reserved, also before their provider configuration is saved. A custom model API cannot take one (A9) [BR-008].
   - A display name of whitespace only is empty. Two display names that differ only in capital letters, or in whitespace at the start or the end, are the same (A10). The system keeps the name as the user gave it.
   - After a key is saved, the system never shows any part of it again: not the whole key, and no prefix, suffix or masked part taken from it. It shows only whether a key is saved, and lets the user replace it (S1, S3, A1).
   - V1 promises no model that runs on the user's computer, and needs none installed or tested. V1 puts the four built-in providers first [BR-005]. A compatible model service on the user's computer can work as a custom model API. V1 neither tests nor promises it, and it is not a feature of its own.
   - Open for technical research, with no product decision now: the API protocols of a custom model API (open question 4), and what each built-in provider needs and allows (open question 3). Also whether the user can change the API protocol of a saved custom model API (open question 9).
   - Also open for evidence: the provider ID strings, and the lists of default models. How a saved key is protected is an architecture item (UC-003 Note 34).
