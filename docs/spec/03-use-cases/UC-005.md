## Goal

The user wants DeckAgent to make decks with models they choose. They have accounts with one or more model providers and a key for each, or a model service of their own. They have no model ready yet, or want more models or another provider, or a key they gave no longer works. They want the models ready without losing the request they were preparing.

## Preconditions

- **Trigger:** The user chooses to set up models. Examples: from the request area (UC-003 A28), or at the first start. Also after a request found no selectable model (UC-003 A17).
- **Preconditions:** DeckAgent runs on the user's computer. A request can be active in a chat while the model setup is open (A12).
- **Evidence:** [observed: owner report (the option to add or change models opens the model setup dashboard); not recorded] [assumed: the first start as a trigger]

## Active interactions

Every flow below is Active in the ideal product; this use case records no Closed flow. Nothing here says which version takes a flow.

How to read the interactions:

- The main flow saves a new provider configuration and adds models to it. The user can save several provider configurations, one at a time (Notes 10 and 11).
- A provider configuration connects to a built-in provider or to a custom model API (S2, S3). Each provider ID has at most one saved provider configuration [BR-008]. The provider ID of a saved provider configuration never changes; to use another provider, the user adds a provider configuration.
- The user then chooses among the selectable models for a chat (UC-003 A27). Choosing a model for a chat is not part of this use case.
- The key belongs to the user's own account with the provider (Vision P-1). How and where the system keeps the key is not part of this use case.
- Step IDs keep their numbers, also since S6 moved before S5 on 12-10-2026.

Stops, restarts and sends again no request. Returns to S1
    end

        User->>DeckAgent: Removes an added model from a provider configuration, and saves
        DeckAgent-->>User: Removes the model from the added models of this provider configuration only. Deletes and changes nothing at the provider [FR-059]
        DeckAgent-->>User: Keeps the provider configuration and its other added models. The model is no longer selectable in any chat
        note over DeckAgent: A chat that selected it has no selected model, as UC-003 A41 says. selects no other model. Changes no conversation, request, attachment or deck. Adding the model again later makes it selectable. it becomes the selected model of no chat by itself. Returns to S1

        note over DeckAgent: Adds no provider configuration the user did not save. Shows the conversation, the request text and the attachments as they were. Selected model of the chat removed: shows that the chat has no selected model, as UC-003 A41 says. Sends no request. Ends
    end
    opt A8 · Add models to a saved provider configuration (at S1)
        User->>DeckAgent: Chooses to add models to a saved provider configuration, for example one saved with no added model
        DeckAgent-->>User: Shows the provider configuration with its display name, its provider ID and its added models. Lets the user get the model catalog of its provider, as S6 says. Keeps the other provider configurations as they were [FR-058]
    end
    opt A10 · Display name not valid (at S1, S4)
        DeckAgent-->>User: When the user saves a provider configuration whose display name is empty, or another saved provider configuration has it: saves nothing of this change [BR-008] [FR-057]
        DeckAgent-->>User: Empty display name: says that the provider configuration needs a display name. Display name in use: says that another saved provider configuration has it
        note over DeckAgent: Keeps what the user gave, so the user can give another display name and save again. Sends no request. At S1 returns to S1. at S4 returns to S3
    end
    opt A11 · Delete a provider configuration (at S1)
        User->>DeckAgent: Deletes a saved provider configuration that no active request uses
        DeckAgent-->>User: Deletes the provider configuration and its added models from DeckAgent. Deletes and changes nothing at the provider, also not the user's account [FR-063]
        DeckAgent-->>User: Keeps every other provider configuration as it was, and every chat with its conversation and its deck
        note over DeckAgent: A chat whose selected model belonged to it has no selected model, as UC-003 A41 says. selects no other model. Lets the user add the same provider again later as a new provider configuration [BR-008]. no chat takes its earlier selection again then. Says that the provider configuration was deleted. Sends no request. Returns to S1
    end
    opt A12 · Provider configuration in use (at S1)
        DeckAgent-->>User: When the user tries to delete a provider configuration that an active request uses: does not delete it, and keeps it with its settings and its added models [FR-064]
        DeckAgent-->>User: Says that an active request uses it, so it cannot be deleted now. Does not stop the request, send it again or move it to another model
        note over DeckAgent: Lets the user delete it after the request finishes, fails or is stopped (A11). Lets the user delete another provider configuration that no active request uses (A11). Returns to S1
    end
    opt A13 · Restore the default models (at S1)
        User->>DeckAgent: Chooses to restore the default models of a provider configuration whose built-in provider has them, and confirms or cancels [BR-005]
        DeckAgent-->>User: Says that restoring replaces the added models with the default models, and asks the user to confirm. Changes no added model before the user answers [FR-062]
        alt Cancelled
            DeckAgent-->>User: Keeps every added model as it was
        else Confirmed
            DeckAgent-->>User: Makes the added models exactly the default models [BR-005]. Removes each other added model
            note over DeckAgent: A chat whose selected model was removed has no selected model, as UC-003 A41 says. selects no other model. Changes no other provider configuration. Sends the provider no request to run a model. Says which added models changed
        end
    end

## Behavior constraints

- A failed request to the provider removes no provider configuration and no added model (UC-003 A18, Note 6). Getting the model catalog changes no added model (S6, A7).
- The key is never shown in the conversation, and no part of a saved key is shown again after it is saved (S1, S3, A1, Note 14).
- A provider configuration that an active request uses is never deleted (A12). A failed save (A5, A6, A9, A10) saves nothing.
- This use case changes the saved provider configurations and their added models. Choosing a model for a chat or a request is UC-003 A27 (Note 1).

Proposals, to be confirmed against recordings.

- **Postconditions:**
  - Main flow: a provider configuration is saved with its provider ID, its display name and its added models. The user can choose among them for a chat. Saving shows neither that the provider accepts the key nor that it runs a model.
  - A1: later requests through the provider configuration use what the user changed. Its provider ID and its added models stay.
  - A2: the model is no longer among the selectable models. Nothing changed at the provider.
  - A8: the provider configuration has the models the user added.
  - A11: the provider configuration and its added models are no longer in DeckAgent. Every chat and deck is as it was.
  - A13: confirmed, the added models are exactly the default models. Cancelled, the added models are as they were.
  - The conversation, the request text and the attachments are as they were.
- **Minimal guarantee:** Whatever branch fails or is left:
  - What the user saved stays as saved. Exceptions are a model the user removed (A2) and a provider configuration the user deleted (A11).
  - No provider ID changes. A provider configuration that an active request uses is never deleted (A12).
  - A failed request to the provider removes no provider configuration and no added model (UC-003 A18).
  - Getting the model catalog changes no added model (S6, A7).
  - The key is never shown in the conversation.
  - The conversation, the request text and the attachments are as they were.

## Notes

1. This use case changes the saved provider configurations and their added models. Choosing a model for a chat or a request is UC-003 A27. One use case, not two: adding, changing, removing, restoring and deleting share the goal of ready models.
2. A refused key or a refused model ends the request (UC-003 A18). A18 does not go to this use case. The user can also choose another selectable model instead (UC-003 A27). The user can change the provider configuration here (A1), then send a new request.
3. UC-003 A17 and A28 go to this use case. A17 brings a request that found no selectable model. A28 brings a user who chose to set up models.
4. How and where the system keeps the key is an ADR matter. The proposed boundary B-3 in the vision is related.
5. A provider usage limit is a property of the user's provider account (Vision P-1). This use case shows no limit and no price.
6. When a model fails, the system does not move to another model by itself. It ends the request and keeps the selected model (UC-003 A11, A18, Note 27; FR-019). This use case does not change that behavior. Until 2026-10-12, this note said it was not decided.
7. Design decision (owner, 2026-10-11): the user sets up a model with their own key inside DeckAgent. No developer prepares the model for them. Considered: a model set up outside the user's own steps, not selected. Why: the user brings their own key (Vision P-1). The owner wants users to finish the setup without a developer's help. Which providers and models are offered stays open (open question 4). This note takes no flow.
8. Design decision (owner, 2026-10-11, revised the same day): minimum model setup. Replaced in part by Note 9 (owner, 2026-10-12), which replaced one provider configuration with several. One model no longer runs every request.
   - Earlier direction: one model set up at a time, which the user could replace.
   - Revised decision: the product needs only one working model, set up with the user's own key. That model runs every request of the journey: generate, preview and refine.
   - Why: the core outcomes come before a wider management of models.
   - Future candidates, with no version assigned: several saved models, switching between them, replacing a model, and a model per request.
   - The behavioral model stays open to several models and providers (Vision P-1). Since 2026-10-12, S4, S6 and S5 say three things. Provider configurations are saved, models are added to them, and selectable models can be chosen. This note takes no flow.
9. Design decision (owner, 2026-10-12): one provider configuration, with all its available models. Replaces in part Note 8. Replaced in part by Note 10 (owner, the same day), which allows several provider configurations, with models the user adds.
   - A provider configuration is one saved connection to a model provider. It holds a display name, the user's key and what the system needs to reach the provider.
   - The display name is the user's own text. It never says which provider the provider configuration connects to. The system does not rename it.
   - Example: the display name is "DeepSeek". The provider configuration connects to Gemini with a Gemini key. The name stays "DeepSeek".
   - The available models of a provider configuration come from the provider it connects to. They never come from its display name.
   - The user chooses the selected model among the available models. One model is selected at a time. It belongs to the provider configuration that gives access to it.
   - The models the user can choose from are grouped by provider configuration. Each group is named by the display name of its provider configuration.
   - One provider configuration at a time meant one group for the user. A later decision allows several, and so several groups. The grouping stays the same.
   - One provider configuration was one slot, not a fixed provider. The limit was the value of a business rule, retired on 12-10-2026 (Note 10).
   - The user can replace the key and change the display name. A saved key replaces the earlier key. It adds no second provider configuration.
   - Leaving the model setup without saving applies no unsaved change. It does not undo a change already saved. Replacing the key does not send a failed request again.
   - Future candidates, with no version assigned: a second provider configuration, and several with their own keys. Also choosing among them and removing one.
   - Open then: how the provider is set, and which models count as available models. Note 10 settles both. How a selected model works is UC-003 Note 25 (owner, 2026-10-12).
   - Why: the owner wants to test different providers through one provider configuration. This note takes no flow.
10. Design decision (owner, 2026-10-12): several provider configurations, and models the user adds. Replaces in part Notes 8 and 9. Replaced in part by Note 11 (owner, the same day). A provider configuration keeps its provider ID, so its provider never changes.
   - The user can save several provider configurations. Two can connect to the same provider with different keys. No number of them is set.
   - The user can change the provider, the key and the display name of a saved provider configuration (A1). A change of provider keeps the display name.
   - The model catalog and the added models are different. The user chooses which models to add, from the model catalog or by model ID (S6).
   - A model ID is saved without a check with the provider. A provider that refuses it at a request ends that request (UC-003 A18). The added model and the provider configuration stay.
   - A missing model catalog leaves adding by model ID possible (A7). It is not a failed request, and it makes no added model unselectable.
   - A change of provider keeps the models added for the earlier provider, but they are not selectable. The system gives no model ID to another provider by itself.
   - The user can remove an added model (A2). Removing it changes nothing at the provider. A chat that selected it chooses again (UC-003 A40).
   - The model setup is the Models part of the settings.
   - Considered: one provider configuration (Note 9), and every model a key can use as an available model. Neither is kept.
   - Open then: a change back to an earlier provider, and a change of address. Also removing a whole provider configuration, and display names. Note 11 settles them.
   - Why: not recorded. A1, A2, A7 and A8 follow this note since 2026-10-12. A version file takes a flow; a note never does.
11. Design decision (owner, 2026-10-12): model provider management. Replaces in part Note 10.
   - A provider configuration is a saved connection to a model service, not only a key. It connects to a built-in provider or to a custom model API.
   - A custom model API has a provider ID, a base URL, an API protocol and, when needed, a key [BR-006]. Two can use the same API protocol.
   - Each provider ID has at most one saved provider configuration [BR-008]. A built-in provider can be added again after its provider configuration is deleted.
   - The provider ID never changes after saving. The user can change the key, the base URL and the display name (A1). To use another provider, the user adds a provider configuration.
   - The display name is not empty, and no other saved provider configuration has it (A10). It never sets the provider ID.
   - Getting the model catalog adds no model and changes no selection (S6). When it fails, adding a model ID by hand stays possible (A7).
   - Restoring the default models needs the user's confirmation first (A13). Cancelling changes nothing.
   - Deleting a provider configuration removes it and its added models from DeckAgent only (A11). Chats and decks stay. No chat gets another model by itself.
   - The user cannot delete a provider configuration that an active request uses, also one that waits for an answer (A12). The request is not stopped for it.
   - Superseded: a change of provider, models kept from an earlier provider, and two provider configurations for one provider (Note 10). The requirement for a change of provider is retired.
   - The model setup holds built-in providers, custom model APIs, the model catalog and the saved provider configurations. The organization came from a reference product. It fixes no interface design (UCG-13).
   - Why: not recorded. A1, A2 and A7 to A13 follow this note since 2026-10-12. A version file takes a flow; a note never does.
12. Design decision (owner, 2026-10-12): adding a provider, active requests, restoring default models and removed models. Adds to Note 11.
   - S2 offers only built-in providers that no saved provider configuration uses. A saved one stays open to change (A1).
   - The provider ID is still checked when the user saves (A9). This holds also for a custom model API.
   - A request keeps the settings it started with until it ends, also for the user's answer. A saved change applies to later requests (A1).
   - A confirmed restore makes the added models exactly the default models. Other added models are removed (A13).
   - A chat whose selected model was removed has no selected model. The system says so when the user comes back to the chat (UC-003 A41).
   - A model or a provider configuration added again becomes the selected model of no chat by itself (A2, A11).
   - This settles three open questions: active requests, a restore, and a model added again. Why: not recorded. S2, S5, A1, A2, A4, A9, A11 and A13 follow this note since 2026-10-12.
13. Design decision (owner, 2026-10-12): built-in providers, base URLs and default models. Adds to Notes 11 and 12.
   - The built-in providers are set [BR-005]. Their provider IDs are not set yet.
   - Custom model APIs stay, so that the user can connect other model services. Their API protocols wait for technical research (open question 4).
   - The base URL of a saved provider configuration can change where its provider allows it [BR-006]. No built-in provider is assumed to allow it.
   - The base URL of a custom model API can still change (A1).
   - DeckAgent sets the default models of each built-in provider that has them, with each release [BR-005]. The model catalog does not set them.
   - Not decided: their model IDs, and whether a new provider configuration starts with them (open question 6). Note 14 settles the second (owner, 2026-10-13).
   - This settles part of open questions 3 and 4. Why: not recorded. A1 follows this note since 2026-10-12. A version file takes a flow; a note never does.
14. Design decisions (owner, 2026-10-13): first setup, default models, provider IDs, display names, keys and local models.
   - With no selectable model, the system guides the user to the model setup (UC-003 A17). It need not open the model setup by itself.
   - A new provider configuration of a built-in provider starts with the default models DeckAgent sets for that release, where it has them (S4) [BR-005]. Their model IDs are still open.
   - The default models of a built-in provider can change between releases. A release never replaces, removes or changes a model the user added. Restoring the default models stays as A13 says.
   - The provider IDs of built-in providers are stable. They stay reserved, also before their provider configuration is saved. A custom model API cannot take one (A9) [BR-008].
   - A display name of whitespace only is empty. Two display names that differ only in capital letters, or in whitespace at the start or the end, are the same (A10). The system keeps the name as the user gave it.
   - After a key is saved, the system never shows any part of it again: not the whole key, and no prefix, suffix or masked part taken from it. It shows only whether a key is saved, and lets the user replace it (S1, S3, A1).
   - The product promises no model that runs on the user's computer. The four built-in providers come first [BR-005]. A compatible model service on the user's computer can work as a custom model API. It is not a feature of its own.
