## Situation and goal

- The user has a deck with slides and sees something to change. Examples are one slide, the tone of the whole deck, or a missing slide.
- Or a first draft stopped or failed early, and the user wants to go on from its confirmed outline.
- The user wants the system to make the change from a request in their own words.
- The user does not want to rebuild the deck. They want everything they did not ask to change to stay as it is.

## Trigger and preconditions

- **Trigger:** The user sends a request in a chat that has a confirmed outline or a deck with slides.
- **Preconditions:** The chat has a confirmed outline, a deck with at least one slide, or both. The system is not working on another request.
- **Evidence:** [observed: napkin-report (after the deck was ready, the user sent a follow-up request in the same conversation)]

## Main flow

- S1 to S3 call UC-003 S1 to S3. The request is prepared and sent there, and the system works there. Writing the request text is UC-003 S1. Every other way to enter the request, including the choice of model, is an alternative flow of UC-003.
- S4 ends the request, as UC-003 S4 says. S4 also shows what this request changed.
- The main flow covers a clear request. It says what to change and where: named slides, several slides or the whole deck. The request can also ask for new slides.
- The system changes only the slides in the scope the request states. It leaves every other slide as it was. It asks for no approval first.
- The system shows no outline for a follow-up request.
- A request whose scope is unclear goes to A1 to A4. A request that does not say what to change goes to A10 or A6.
- The request can come after a first draft that stopped or failed (UC-001 A10, A11). The deck then has fewer slides than the confirmed outline, or none. The first draft does not count as finished.

### S1 · Describe the change

- **User:** Describes the change in the request area. The user says what to change, and on which slides or on the whole deck.
- **System:**
  - Shows what the user wrote in the request area, as UC-003 S1 says.
- **Reqs:** none
- **Evidence:** [observed: napkin-report (the request named a slide by number and title and said what to add)]

### S2 · Send the request

- **User:** Sends the request.
- **System:**
  - Sends the request as UC-003 S2 says.
- **Reqs:** none

### S3 · Watch the change apply

- **User:** Waits and watches the deck canvas.
- **System:**
  - Shows the **status message** as UC-003 S3 says.
  - Says in the conversation which slides it is changing.
  - Changes each slide in the scope the request states, in place. The slide keeps its place in the deck.
  - Builds each new slide the request asks for, at the place the request names.
  - Uses the confirmed outline, the slides and the material given earlier in the chat when the request needs them.
  - Leaves every slide outside that scope as it was.
  - Builds and shows no outline.
- **Reqs:** FR-?

## Alternative flows

### A1 · Scope of the change is unclear

- **At:** S2
- **End:** Same step
- **When:** The request does not make clear which slides the change reaches. An example is "make it more formal" with no slide named.
- **System:**
  - Changes no slide yet.
  - Says in the conversation that it cannot tell which slides the change reaches.
  - Offers two outcomes: apply to every slide, or keep the instruction and change no slide now.
  - Offers a third outcome, apply to new slides only, when the request asks for a new slide.
  - Keeps the request open while it waits, as UC-003 A38 says. The choice is part of the same request.
  - The choice leads to A2, A3 or A4.
- **Reqs:** FR-020, FR-?
- **Evidence:** [observed: napkin-report (a request for a new tone for the whole deck and one new slide got a question with three outcomes)] [observed: napkin-report (the question starts "I've updated the deck's tone", so what changed before the question is not known)] [observed: owner report (the third outcome is not offered when the request asks for no new slide); not recorded] [assumed: no slide changed before the user chose; the image does not show the deck canvas]
- **Updated at:** 12-10-2026

### A2 · Apply the change to every slide

- **At:** S2
- **End:** Continues at S3
- **When:** The user chooses, after A1, to apply the change to every slide.
- **System:**
  - Replaces every existing slide with a new version made with the instruction.
  - Builds each new slide the request asks for with the same instruction.
  - Asks nothing more before it replaces the slides.
- **Reqs:** FR-?

### A10 · Offer directions for unclear feedback

## Postconditions and minimal guarantee

Proposals, to be confirmed against recordings.

- **Postconditions:**
  - Main flow: the slides in the scope the request states show the change. Every other slide is as it was.
  - A7 and A11: each finished slide shows the change. Every other slide is as it was before the request.
  - A2: every slide is a new version made with the instruction.
  - A3: only new slides were added. Existing slides are as they were.
  - A4: no slide changed. The instruction is kept for later slides.
  - The conversation holds the request and the closing message.
- **Minimal guarantee:** Whatever branch fails or is interrupted:
  - The request text is kept in the conversation.
  - Each slide is either as it was before the request or fully changed.
  - The user does not have to enter the request again.

1. Design decision (owner, 2026-10-08): a request that names the slides it changes is applied in place. Every other slide stays as it was.
2. Design decision (owner, 2026-10-08): a follow-up request never shows an outline. The outline checkpoint applies to the first draft only. The internal data structure is a backend concern, not part of this use case.
3. Design decision (owner, 2026-10-08): a request that would change slides it does not name gets outcomes before any slide changes (A1 to A4). A request that asks for no new slide is not offered "new slides only". Replaced in part by Note 13 (owner, 2026-10-11): a clear request that reaches slides it does not name gets no outcomes first.
4. Design decision (owner, 2026-10-08): the system protects every slide the request does not name. It does so even when the change leaves the deck inconsistent, for example a repeated number.
5. Design decision (owner, 2026-10-08): the user can choose another model for a follow-up request, as for any request (UC-003 A27).
6. One use case, not two. Both paths share the goal, the trigger, the preconditions and the result. The user does not choose the path. The system chooses it from the request. The whole-deck path adds one decision, so it is an alternative flow. Since 2026-10-11, a clear whole-deck request is in the main flow. Only an unclear scope adds the decision (A1, Note 13).
7. Changes the user makes by hand, without asking the system, are a different goal. They are UC-007. Note 1 covers the main flow. There, a change by hand on a slide the request does not name stays.
8. A request uses the material the user gave earlier in the chat as context for its changes and new slides. An example is a file attached to an earlier request. The material changes no slide by itself.
9. Proposal, not confirmed (owner, 2026-10-10): "No slide is half changed" (A7) and "Each slide is either as it was before the request or fully changed" (minimal guarantee) are explored, not chosen. They state what the user sees, not how the system saves a slide. Whether DeckAgent commits to them is open. Confirmed in part by UC-003 Note 20 (owner, 2026-10-11): an unfinished change never replaces the last finished state of a slide.
10. A failure or a stop at S3 also runs the flow of UC-003 for it: A11, A18, A19 or A31. This use case adds only what is specific to the deck. A7 does so for a stop. Since 2026-10-11, A11 does so for a failure. Before, no flow here said which slides changed before a failure.
11. A request that changes the look of slides it does not name goes to A1, like any such change. Since 2026-10-11, only a look change with an unclear scope goes to A1 (Note 13). A8 adds what is specific to a change of look. Content and look can change in one request. A8 then applies to the look only.
12. A request for another deck from this one, for another use, is UC-011. This use case changes the deck in place and makes no second deck.
13. Design decision (owner, 2026-10-11): a follow-up request changes what the user asks, at the scope the user states.
   - It can change one slide, several slides or the whole deck.
   - Clear change and clear scope: the system applies it without asking for approval first.
   - Unclear change or unclear scope: the system asks before it changes any slide.
   - Content outside the requested scope stays as it was (Notes 1 and 4).
   - Considered for scope: named slides only; whole-deck changes with an extra approval. Considered for approval: always ask, not selected; ask by risk, a future candidate.
   - Why: the user does not split a clear whole-deck request into many small ones. An extra approval adds a step when the user already gave the change and the scope. Asking about an unclear request, asking for approval and getting an earlier deck back are separate concerns.
   - Replaces in part Note 3. The main flow and A1 follow this note since 2026-10-11. A1 asks only when the scope is unclear. This note selects no flow.
14. Design decision (owner, 2026-10-11): feedback that does not say what to change. Three levels are kept apart. Status: the owner approved guided clarification as V1 behavior. A10 describes it, and A6 describes the fallback. `versions` selects no flow for them yet. This note selects no scope.
   - Guided clarification (B1), approved: the system uses the deck and the chat to offer directions to improve. Example: "Slide 3 doesn't look right" gets content, readability or layout.
   - The user chooses a direction or explains more. Only then does the deck change.
   - Basic clarification (A), kept as a fallback: the system asks what to change. It does so when it has no grounded direction to offer.
   - Design diagnosis (B2), a future candidate with no version: the system judges a slide against its purpose. It names problems, says why they matter and proposes changes.
   - Why: guided clarification helps users without design knowledge say what they want. Design diagnosis needs a more reliable judgement of design. Its feasibility is not known.
   - A10 and A6 cover feedback with or without a slide named. Until 2026-10-11, A6 said only that it could not tell what to change, then ended.
15. Stop, failure and undo of a follow-up request: UC-003 Notes 17 to 20 hold the owner decisions of 2026-10-11. A7 and A11 follow them. Open questions 1 to 3 concern a later try-again action (UC-003 Note 18). A finished request is not undone. The user who dislikes its result sends a new request here (UC-008 Note 5).
16. Design decision (owner, 2026-10-11): a new request after a first draft that stopped or failed is a follow-up request here (UC-001 A10, A11).
   - It uses the confirmed outline and the finished slides as context.
   - This holds also when no slide was finished.
   - The request shows no second outline.
   - The first draft does not count as finished.
   - Considered: UC-001 finishes the first draft itself; a new first draft when no slide exists. Neither is selected.
   - Why: not recorded. This note selects no flow.
17. Clarifying questions (A1, A6, A10): the answer is part of the same request. The request stays open while the system waits. The owner decision of 2026-10-11 is UC-003 Note 22.
18. Design decision (owner, 2026-10-11): whole-deck refinement, not full deck regeneration.
   - V1 allows changes to one slide, several slides or every slide through follow-up requests (Note 13).
   - A separate workflow for full deck regeneration is not selected for V1. It would let the user change the topic, purpose or structure of the deck completely in this chat.
   - Three outcomes were considered for such a request. Append: add new slides to the deck. Regenerate all: replace the deck with a newly drafted one. Preserve direction: keep the deck's topic or direction, and apply the compatible parts of the instruction.
   - These outcomes are not specified. The system does not always offer them. Whether it asks depends on how clear the intent is (Note 13). A1 to A4 settle an unclear scope, not a new topic.
   - Why: the core outcomes come first. Feasibility and the effect on architecture are not assessed.
   - It adds no outline checkpoint (Note 2), no second deck in the chat (Note 12) and no undo of a request (UC-008 Note 5).
   - Future candidate, with no version assigned. This note selects no flow.
