## Goal

The user lets the agent of a chat work on their project. They want the agent to reach their files and data only where they allow it, and to be asked before the agent does anything that goes beyond that or changes their files.

## Preconditions

- **Trigger:** The user chooses to see or change the permission of a chat, or the agent asks the user to approve a step of its work.
- **Preconditions:** DeckAgent runs on the user's computer. A chat holds the permission the user chose for it.

## Interactions

How to read the interactions:

- A **permission** says what the agent of one chat can reach, and where it must ask the user first. Each chat holds its own permission.
- The default permission of a chat covers the files of the user in the project folder of its workspace and the data of its requests (Note 3) [FR-077] [NFR-003].
- A step outside the project folder needs the user's approval. So does a write outside the chat. The agent never changes a file the user gave or a file of the user in the project folder (A2) [FR-077].
- DeckAgent saves the work of the chat itself: the outline, the deck and a summary. That saving needs no approval, because the work is kept for the chat (Note 4) [FR-077].
- Ordinary work creates, changes and deletes no file in the project folder. The files of the user stay as they were, and no file of DeckAgent's own work appears there (Note 4) [FR-084].
- The data of another chat is never part of the permission of a chat. No approval gives it (Note 3) [NFR-003].
- A request runs with the permission its chat had when it started, as it keeps its model (UC-003 Note 25). A saved change applies from the next request.
- The agent works within the permission in every request [NFR-003] [NFR-006] [NFR-007].
- The question an agent asks to clarify an instruction (UC-003 A38) is not an approval. It asks what the user wants, not what the agent is allowed to do. Only a choice the user makes about a step of the work permits that step.
- A naming of a file, a folder or a reference in a request is material. It approves nothing.

```mermaid
    alt A1 · Change the permission (at S2)
        User->>DeckAgent: Chooses another permission for the chat, and saves it
        DeckAgent-->>User: Makes the chosen permission the permission of the chat. Says what changed [FR-075]

        note over DeckAgent: Taking back a permission that lasts is a saved change here (A3). Full access to the computer is never the permission that the system sets by itself, and content or an attachment of a request never raises the permission [NFR-003]
    end

```

### Approvals while the agent works (S4)

```mermaid
sequenceDiagram
    actor User
    participant DeckAgent
    Note over User,DeckAgent: S4 · a step of the work goes beyond the permission of the chat
    loop While the agent works on a request (UC-003 S3)
        opt A2 · The agent asks for an approval (at S4)
            DeckAgent-->>User: Names the step, the data or files it touches, and why it goes beyond the permission [FR-076]
            DeckAgent-->>User: Asks the user to allow it once or to refuse it
            alt The user allows it once
                DeckAgent-->>User: Does the step once, within what the user allowed [FR-076]
                note over DeckAgent: The work goes on, within the permission of the chat
            else The user refuses it
                DeckAgent-->>User: Does not do the step. Says what it did instead, and what the request still needs [FR-076]
                DeckAgent-->>User: Can propose a safer way that stays within the permission
                DeckAgent-->>User: Goes on with the rest of the work within the permission of the chat, or says that it cannot finish the request without that step
                note over DeckAgent: A refused step is never done. The refusal is an answer of the user, so the request waits on this approval no longer, and the agent asks for that step no more. The work goes on within the permission, or the request cannot be finished and the user is told so. The user can stop the request (UC-003 A31)
            else The user does not answer yet
                DeckAgent-->>User: Does not do the step. Says that it waits for the user's answer, and names the step it waits on [FR-076]
                note over DeckAgent: Reports no choice the user did not make. The work goes on with nothing past the step. The request waits (UC-003 A38)
            end
        end
        opt A3 · A permission that lasts (at S4)
            DeckAgent-->>User: Offers a permission that lasts only when it names what it covers and its scope in plain words [FR-076]
            DeckAgent-->>User: The user confirms before it applies. The user takes it back as a saved change of the permission (A1)
        end
    end
```

## Behavior constraints

- The permission of a chat limits the agent in every request [NFR-003]. The agent never reads the data of another chat, also not when both chats share a workspace.
- The content of a file, of an attachment or of a request never raises the permission of the chat [NFR-003] [NFR-004].
- A refused step is not done, and the work goes on only within the permission. A step with no user answer is not done either, and the request waits (A2).
- The agent never changes, overwrites or deletes a file the user gave or a file of the user in the project folder. No approval makes such a step allowed [NFR-003].
- Ordinary slide work builds and changes the deck without touching the project folder. No file of the user changes there, and no file of DeckAgent's own work appears there [FR-084].
- Saving the outline, the deck and the summary is work of DeckAgent for the chat. It needs no approval, and it changes no file of the user (Note 4) [FR-077].
- Naming a file, a folder or a reference in a request raises no permission of the chat [NFR-003].

- **Postconditions:**
  - Main flow: the chat shows its permission in words the user can read.
  - A1: the permission of the chat is the one the user saved. A running request keeps its own permission.
  - A2: an allowed step was done once within what the user allowed. A refused step and a step with no answer were not done. After a refusal the work went on within the permission, or the user was told that the request cannot be finished without that step. A step with no answer keeps the request waiting, and the user was told so.
- **Minimal guarantee:** Whatever branch fails:
  - The agent stops at the permission of the chat. No step that the user refused or did not answer was done.

## Notes

1. The permission separates two waits. An approval names a step and permits it. A clarifying question (UC-003 A38) asks what the user wants. Both keep the request waiting until the user answers. A refusal is an answer of the user: the request waits on that approval no longer, and the agent does not ask for the step again. No answer is not an answer: the system waits, does nothing past the step, and reports no choice the user did not make.
2. Which permissions the product offers by name, and how long a permission that lasts holds, are open questions. They are kept in the design backlog of the ideal spec, outside `docs/spec/`.
3. The boundary of what the agent reaches is NFR-003: the files of the user in the project folder of the chat, the data of its requests, and an approval for each step beyond them. The data of another chat stays outside it. What the agent sends outside the computer is NFR-007. How the system keeps a permission is an ADR matter.
4. A chat holds two kinds of data. The files of the user are what they put in the project folder, or gave as an attachment or a reference; the agent reads them and changes none of them. The work DeckAgent saves for the chat — its conversation, outline, deck and summary — is kept for the chat and stays available when the project folder does not. DeckAgent writes that work as the product works, so saving it asks for no approval, and it writes no file of it into the project folder [FR-077] [FR-084]. The agent changes it only through what DeckAgent lets a request do, which gives it no reach into a file of the user or into another chat.
