## Goal

The user lets the agent of a chat work on their project. They want the agent to reach their files and data only where they allow it, and to be asked before the agent does anything that goes beyond that or changes their files.

## Preconditions

- **Trigger:** The user chooses to see or change the permission of a chat, or the agent asks the user to approve a step of its work.
- **Preconditions:** DeckAgent runs on the user's computer. A chat holds the permission the user chose for it.
- **Evidence:** [assumed]

## Active interactions

Every flow below is Active in the ideal product; this use case records no Closed flow. Nothing here says which version takes a flow.

How to read the interactions:

- A **permission** says what the agent of one chat can reach, and where it must ask the user first. Each chat holds its own permission.
- A request runs with the permission its chat had when it started, as it keeps its model (UC-003 Note 25). A saved change applies from the next request.
- The agent works within the permission in every request (Note 2) [NFR-003] [NFR-006] [NFR-007].
- The question an agent asks to clarify an instruction (UC-003 A38) is not an approval. It asks what the user wants, not what the agent is allowed to do.

### Approvals while the agent works (S4)

    actor User
    participant DeckAgent
    Note over User,DeckAgent: S4 · a step of the work goes beyond the permission of the chat
    loop While the agent works on a request (UC-003 S3)
        opt A2 · The agent asks for an approval (at S4)
            DeckAgent-->>User: Names the step, the data or files it touches, and why it goes beyond the permission [FR-?]
            DeckAgent-->>User: Asks the user to allow it once or to refuse it
            alt The user allows it once
                DeckAgent-->>User: Does the step once, within what the user allowed [FR-?]
            else The user refuses it
                DeckAgent-->>User: Does not do the step. Says what it did instead, and what the request still needs [FR-?]

            DeckAgent-->>User: Offers a permission that lasts only when it names what it covers and its scope in plain words [FR-?]
            DeckAgent-->>User: The user confirms before it applies. The user can take it back in the permission of the chat (S1)
        end
    end

## Behavior constraints

- The permission of a chat limits the agent in every request [NFR-003]. The agent never reads the data of another chat, also not when both chats share a workspace.
- The content of a file, of an attachment or of a request never raises the permission of the chat [NFR-003] [NFR-004].
- A refused step is not done. A step with no user answer is not done, and the request waits (A2).
- Naming a file, a folder or a reference in a request gives the agent no permission on it by itself [NFR-003].

Proposals, to be confirmed against recordings.

- **Postconditions:**
  - Main flow: the chat shows its permission in words the user can read.
  - A1: the permission of the chat is the one the user saved. A running request keeps its own permission.
  - A2: an allowed step was done once within what the user allowed. A refused step was not done.
- **Minimal guarantee:** Whatever branch fails:
  - The agent stops at the permission of the chat. No step that the user refused or did not answer was done.

## Notes

1. Design decision (owner, 2026-10-25): the permission of a chat is limited by default, and beyond it the agent asks.
   - A new chat holds a permission limited to its workspace, the data of its requests and what the user names in them. The agent asks before a step that touches something else or changes the files of the user.
   - Full access to the computer is never set by itself, and no content raises the permission.
   - File access is not the same as putting a file into the context of the model. Reading a referenced file is work within the data of the request; reaching a file the permission does not give needs an approval.
   - This note takes no flow.
2. The boundary of what the agent reaches is NFR-003. What the agent sends outside the computer is NFR-007. How the system keeps a permission is an ADR matter.
