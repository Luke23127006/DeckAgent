## What it is

The user sees a **small thing to fix** in a deck the system made, such as a wrong word or a slide in the wrong place. **Fixing it by hand is quicker** than describing it in a request. The user wants **only that change**, **without waiting for the model** or **risking other slides**.

**Flows to cover**: add, delete, duplicate or move a slide; undo the last change by hand; a part that is not changed by hand; cancel the change. **No FR is written yet**.

## Belongs to

None.

## Why parked

**Changes by hand are not in the MVP**. **What each generation format supports** for changes by hand **is not decided**.

## Reconsider when

Not set by the PO.

## Findings

- **Each generation format states what it supports**. **Changes by hand come first for the formats that look most feasible** (agent estimate, not checked: HTML with Reveal.js, and Markdown with Marp or Slidev); **PPTX, LaTeX, Google Slides, design tools and vector formats wait**. The **level of support per format is not decided**.
- **Editing the Markdown file in VS Code needs the file outside DeckAgent**. **Where the deck source is kept**: `pending`. **Open question**: is it **the file DeckAgent uses**, with changes coming back, or **an exported copy**?
- Whether the **check of each write** (FR-092) **also applies to a change by hand**, and whether the **user edits the theme by hand**: `pending`. A **colour or font the user chose is never a fault** of the check (FR-092).
- **Undo of a change by hand** and **going back to an earlier state** (UC-008 in the backlog) are **settled together**; **read that item first**.
- The **deck source is the working files** of the deck: the **system and the user change the same files**.
- Teacher feedback of 23-10-2026 (11:25 to 12:52 and 18:04 to 20:51): **edit an HTML deck on the canvas**, and a **Markdown deck in their own editor** such as VS Code.
