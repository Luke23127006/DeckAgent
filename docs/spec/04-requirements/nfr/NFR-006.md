---
id: NFR-006
title: "Key kept out of the work and its records"
---

## Requirement

- **Quality attribute:** security
- **Statement:** A saved key reaches only the trusted parts of DeckAgent that send the requests of its provider configuration. The key is never part of what the model receives or can use as working data. It never appears in a conversation, a deck, a record or a file, outside the place where DeckAgent keeps keys. Each request carries only the key of its own provider configuration, to its own base URL.
- **Status:** confirmed
- **Source:** owner decision, 2026-10-13: keys never go into the context of the model or into content the model can use as working data; the trusted parts of DeckAgent can use the provider configuration and its credentials to run the request; owner decision, 2026-10-13: a key never appears in conversations, decks, records or files outside the allowed place, goes only to the valid address of its own provider configuration, and is never used for another provider configuration
- **Updated at:** 13-10-2026

## Verification

### M-1 · Not in what the model receives

- **Conditions:** A provider configuration with the key K1, a distinct marker value. The user sends requests in a chat whose selected model belongs to it. Some requests ask for the key. Some attachments hold instructions to reveal it. Boundary: product-controlled. Provider-dependent conditions: none change the result. A model service records what it receives.
- **Measure:** Whether K1 appears in the content that the model receives, apart from the authorization of the request. Whether K1 appears in a response or in the chat.
- **Method:** Capture the content of each request to the model service. Search it, each response and the chat for K1.
- **Target:** K1 appears in none of them.
- **Met when:** Every run meets the target.

### M-2 · Sent only to its own base URL

- **Conditions:** Provider configuration P1 has the key K1 and the base URL U1. Provider configuration P2 has the key K2 and the base URL U2. The user sends requests in chats whose selected models belong to P1 and to P2. The user also gets the model catalog of each. Boundary: product-controlled. Provider-dependent conditions: none change the result. Model services at U1 and U2 record what arrives.
- **Measure:** Where K1 and K2 are sent. Which key each request carries.
- **Method:** Record every outgoing connection during the runs and what it carries. Search each one for K1 and K2.
- **Target:** K1 goes only to U1. K2 goes only to U2. Each request of P1 carries K1 and never K2. Each request of P2 carries K2 and never K1.
- **Met when:** Every run meets the target.

### M-3 · Not in data that DeckAgent writes

- **Conditions:** The key K1 is saved. The user runs requests that finish, that fail and that the provider refuses for K1. The user then replaces K1 with K2. DeckAgent ends normally once, and unexpectedly once. Boundary: product-controlled. Provider-dependent conditions: none change the result.
- **Measure:** Whether K1 or K2 appears in data that DeckAgent writes on the computer, outside the place where it keeps keys. This data includes chats, decks, records of errors and temporary files. It also includes each message that DeckAgent prints while it runs.
- **Method:** After the runs, search every file that DeckAgent wrote or changed for K1 and K2. Search every message it printed.
- **Target:** Neither key appears outside the place where DeckAgent keeps keys.
- **Met when:** Every search meets the target.

## Not specified

- Whether other programs of the same user on the computer can read a saved key. Pending owner decision.

## Notes

- What the user sees of a key is behavior, not this requirement.
- How and where DeckAgent keeps a key, and whether it encrypts it, is an architecture matter.
