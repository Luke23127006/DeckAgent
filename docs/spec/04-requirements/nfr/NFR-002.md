## Requirement

- **Quality attribute:** performance
- **Statement:** After the user confirms the outline, the first finished slide soon shows in the deck canvas. The wait is measured end to end, so it includes the time of the model provider.
- **Status:** proposed
- **Source:** proposed
- **Why:** A selected flow marks the wait for the first slides as a quality to set. Two parts of this statement are the author's proposal, not confirmed behavior. First, the boundary is end-to-end. A slide needs the model, so a product-controlled boundary would leave out most of the wait. Second, the wait ends at the first finished slide. Trade-off: the target depends on the provider and the model, so it holds only under named conditions.
- **Updated at:** 12-10-2026

## Verification

### M-1 · Time to the first finished slide

- **Conditions:** A chat with a model set up. The user confirmed an outline of four planned slides, drafted from a request with request text only. Boundary: end-to-end, as the proposed statement says. Provider-dependent conditions: the provider, the model and the response time of the provider. Every run names the provider and the model it used. Every run uses the same computer, and the report names it.
- **Measure:** The time between two moments. It starts when the user sends the confirmation of the outline. It ends when the deck canvas shows the first finished slide.
- **Method:** Confirm the same outline many times for each provider and model. For each run, observe both moments as the user sees them, with one clock, and record the time between them. Report the times for each provider and model apart.
- **Target:** not set
- **Met when:** not set
- **Status:** pending
- **Source:** owner decision needed
- **Why:** No decision sets the time, or the share of runs that must meet it.

## Not specified

- The providers and models under which the target must hold. Pending owner decision.
- The range of computers on which the target must hold. Pending owner decision.
