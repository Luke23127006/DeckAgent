---
id: FR-043
title: "Change the key or the base URL of a provider configuration"
---

## Requirement

- **Statement:** The user can give a saved provider configuration a new key or other authentication information [BR-006]. The user can also give it a new base URL, where its provider allows one [BR-006]. The user then saves. The system replaces what changed and says so. It keeps the provider configuration with its provider ID, its display name and its added models, which stay selectable. It keeps the selected model of each chat, and checks no added model with the provider. The change sends no request. After a refused key, the user carries on with a new request.
- **Status:** confirmed
- **Source:** use case flow, and owner decision, 2026-10-11: a failed request is reported, not started again, and the user carries on through a new request; owner decision, 2026-10-12: the user adds the models of a provider configuration, and a saved model is no proof that the key runs it; owner decision, 2026-10-12: the user can change the key, other authentication information and the base URL, and the provider ID stays; owner decision, 2026-10-12: a base URL can change where its provider allows it, and no built-in provider is assumed to allow it
- **Updated at:** 12-10-2026

## Acceptance conditions

### AC-1 · The provider configuration stays

- **Given:** A provider configuration for provider P is saved with the display name "Work AI" and the key K1.
- **When:** The user gives the new key K2 for "Work AI" and saves.
- **Then:**
  - The model setup still shows "Work AI" with provider P as saved.
  - The setup shows no added provider configuration.
- **Check:** deterministic

### AC-2 · The user is told

- **Given:** The state of AC-1.
- **When:** The user gives the new key K2 for "Work AI" and saves.
- **Then:**
  - The system says that the key of "Work AI" was replaced.
- **Check:** judged

### AC-3 · Replacing the key sends nothing

- **Given:** The state of AC-1. Earlier, P refused K1 for the request "a talk on our pilot results", and the conversation reports it.
- **When:** The user replaces the key with K2 and goes back to the chat.
- **Then:**
  - The refused request shows once in the conversation, the same as when it was sent.
  - No request starts.
  - The system does not send the refused request again.
- **Check:** deterministic

### AC-4 · New request after the key is replaced

- **Given:** The state after AC-3. The selected model of the chat is the added model M1 of "Work AI".
- **When:** The user sends the new request "a talk on our pilot results".
- **Then:**
  - The conversation shows it as a new user's message.
  - The refused request still shows once, unchanged.
  - The system works on the new request.
- **Check:** deterministic

### AC-5 · Added models stay after a new key

- **Given:** The state of AC-1 before the replacement. "Work AI" has the added models M1 and M2. Chat X has the selected model M1.
- **When:** The user saves K2 and then chooses to change the model in chat X.
- **Then:**
  - "Work AI" still has the added models M1 and M2.
  - The user can choose M1 and M2.
  - Chat X still has M1 as its selected model.
- **Check:** deterministic

### AC-6 · A new base URL

- **Given:** "Lab" is a custom model API with the provider ID "lab", the base URL U1 and the key K2. It has the added model M1. Chat Y has M1 of "Lab" as its selected model. Test accounts at U1 and U2 record each request they receive.
- **When:** The user changes the base URL of "Lab" to U2 and saves. The user then sends a request in chat Y.
- **Then:**
  - The model setup shows "Lab" with the provider ID "lab" and the base URL U2.
  - U1 and U2 receive no request before the user sends one.
  - U2 receives the request for model M1 with the key K2. U1 receives no request after the change.
  - "Lab" still has the added model M1, and chat Y still has M1 of "Lab" as its selected model.
- **Check:** deterministic

## Notes

- Replacing a key does not show that the provider accepts it. A refusal of the new key is a new failure, as FR-019 says.
- The key is never shown in full, as FR-040 says. Later requests use the new key, as FR-042 says. The provider ID never changes, as FR-061 says.
- After a first draft that ended on a refused key, the new request builds on that draft, as FR-028 says.
- Until 2026-10-12, AC-5 said that the models of the provider configuration follow the new key. The owner decision of 2026-10-12 on added models replaced it.
- Until 2026-10-12, this requirement covered a new key only. The owner decision of 2026-10-12 on connection settings added other authentication information and the base URL.
- A request that is active when the change is saved keeps its earlier settings, as FR-042 says.
- Until 2026-10-12, the user was able to give every provider configuration a new base URL. The owner decision of 2026-10-12 on base URLs limits it to a provider that allows it. AC-6 uses a custom model API.
