---
id: FR-043
title: "Replace the key of a provider"
---

## Requirement

- **Statement:** The user can give a new key for the provider of the model that is set up. The system replaces the old key with it, keeps the model set up and says that the key was replaced. The replacement sends no request. After a refused key, the user carries on with a new request.
- **Status:** confirmed
- **Source:** use case flow, and owner decision, 2026-10-11: a failed request is reported, not started again, and the user carries on through a new request
- **Updated at:** 12-10-2026

## Acceptance conditions

### AC-1 · The model stays set up

- **Given:** Model M of provider P is set up with the key K1.
- **When:** The user gives the new key K2 for P and saves.
- **Then:**
  - The model setup still shows model M with provider P as set up.
  - The setup shows no other change to the models set up.
- **Check:** deterministic

### AC-2 · The user is told

- **Given:** The state of AC-1.
- **When:** The user saves the new key.
- **Then:**
  - The system says that the key of P was replaced.
- **Check:** judged

### AC-3 · Replacing the key sends nothing

- **Given:** The state of AC-1. Earlier, P refused K1 for the request "a talk on our pilot results", and the conversation reports it.
- **When:** The user replaces the key with K2 and goes back to the chat.
- **Then:**
  - The refused request shows once in the conversation, the same as when it was sent.
  - No request starts.
  - The system does not send the refused request again.
- **Check:** deterministic

### AC-4 · New request after the key is replaced

- **Given:** The state after AC-3.
- **When:** The user sends the new request "a talk on our pilot results".
- **Then:**
  - The conversation shows it as a new user's message.
  - The refused request still shows once, unchanged.
  - The system works on the new request.
- **Check:** deterministic

## Notes

- Replacing a key does not show that the provider accepts it. A refusal of the new key is a new failure, as FR-019 says.
- The key is never shown in full, as FR-040 says. Later requests use the new key, as FR-042 says.
- After a first draft that ended on a refused key, the new request builds on that draft, as FR-028 says.
