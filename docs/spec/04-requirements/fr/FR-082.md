---
id: FR-082
title: "Name a reference in the project folder as material"
---

## Requirement

- **Statement:** The user can name a file or a folder in the project folder of the workspace of the chat as material for a request, as a reference. The system shows the reference in the request area, with its name and its state. It does not send the reference and does not read it while the user prepares the request. Naming a reference raises no permission of the chat; the agent reads it within the permission of the chat, when a request uses it [NFR-003]. Naming a reference adds no attachment [BR-001]. A reference does not count toward the number of attachments in a request. A reference is valid only while the intended file can be read at the moment the agent reads it: a ready state the user saw earlier, or the name of the file, shows no successful read. When a read exceeds a safe resource limit, the system does not read beyond that limit and says which material it cannot use. The intended file is the one the user named in the project folder the workspace has then. When that project folder changes, the system checks each reference again against the folder the workspace has now, and it reads no file of another folder in place of the one the user named, also not a file of the same name. A reference the user already sent stays in the conversation as the user's message, and the system claims nothing about whether the file it named can still be read. A chat that stops belonging to a workspace, because that workspace was removed, keeps every reference the user named and did not send: the system deletes none of them, and shows each one in a state that says it cannot be read. The system reads no file of a folder only because a reference once named it there. When the named file or folder cannot be read, for example it is missing or access was taken away, the system shows that state with the reason, as it shows the reason on an attachment it rejects. A reference whose state does not block sending can be sent alone, with no request text and no attachment (FR-015). A reference whose state blocks sending blocks the request like a rejected attachment (FR-015, FR-017). A chat that belongs to no workspace has no project folder, so the user names no new reference in it: a file the user wants the work to use joins the request as an attachment, or the work reads it only after the user approves the step (FR-076).
- **Updated at:** 27-10-2026

## Acceptance conditions

### AC-1 · The reference is shown with name and state

- **Given:** The chat belongs to a workspace whose project folder holds the file "notes.md". The request area holds no request text.
- **When:** The user names "notes.md" as material for the request.
- **Then:**
  - The request area shows the reference with its name "notes.md" and its state.
  - The conversation shows no new user's message, and nothing was sent.
- **Check:** deterministic

### AC-2 · Naming is not sending and not reading

- **Given:** The state after AC-1. A test account with the selected model's provider records each request it receives. The system has produced no plan for any request.
- **When:** The user names the reference and does not send a request.
- **Then:**
  - The provider receives no request, and the system starts no work. The content of "notes.md" joins the data of the request only when a request uses it.
- **Check:** deterministic

### AC-3 · Naming gives no permission

- **Given:** The state after AC-1. The computer holds a folder outside the project folder of the chat, with the file "secret.md" in it. No request of the chat names that folder.
- **When:** The user names "notes.md" as material, and sends a request that uses it.
- **Then:**
  - The permission of the chat is the same as before the naming (FR-077, NFR-003).
  - The work reads nothing of that folder outside the project folder, and no step there is done without an approval (FR-076).
- **Check:** deterministic

### AC-4 · An unreadable reference shows its state with the reason

- **Given:** The project folder of the chat holds no file "old.md", and the user names it.
- **When:** The system records the naming.
- **Then:**
  - The request area shows the reference "old.md" in a state that says it cannot be read, with the reason when it is known, as a rejected attachment shows its reason.
- **Check:** deterministic

### AC-5 · A ready reference can be sent alone

- **Given:** The state after AC-1. The reference is in a state that does not block sending.
- **When:** The user sends the request with the reference and no request text.
- **Then:**
  - The request is sent. The conversation shows the reference as the user's message.
- **Check:** deterministic

### AC-6 · A blocking reference blocks the request

- **Given:** The state of AC-4. The reference "old.md" is in a state that blocks sending. The request area holds no other content.
- **When:** The user tries to send the request.
- **Then:**
  - Nothing is sent, and the reference stays in the request area with its state.
- **Check:** deterministic

### AC-7 · A ready reference that became unreadable is not sent as a source

- **Given:** The reference "notes.md" is shown in a state that does not block sending. The file is then removed from the project folder outside DeckAgent.
- **When:** The user sends the request.
- **Then:**
  - The request is not sent as if "notes.md" can be read.
  - The request area shows the reference in the state that says it cannot be read.
  - The request text stays in the request area, as the user wrote it.
- **Check:** deterministic

### AC-8 · A reference is read only while it can be read

- **Given:** The reference "report.pdf" is in the request, and the system read it during the request. The file is then removed from the project folder outside DeckAgent.
- **When:** The system needs material from "report.pdf" again in the same request.
- **Then:**
  - The system uses the part it read before the file was removed, and no other content in place of the rest.
  - The response says which part of the material it cannot read (FR-086).
- **Check:** deterministic

### AC-9 · A sent reference stays, with no claim about the file

- **Given:** The user sent a request with the reference "notes.md" of the project folder, and the system read it. The file is then deleted outside DeckAgent, and the workspace keeps its project folder.
- **When:** The user opens the chat again and reads that request.
- **Then:**
  - The conversation still shows the request with "notes.md" as the user's message.
  - The system does not say that "notes.md" can be read, and it claims no content of the file that it does not hold.
  - The user names the file again for a new request when it can be read again.
- **Check:** deterministic

### AC-10 · A reference survives the removal of its workspace

- **Given:** The workspace "Alpha" for the folder "C:\ projects\alpha" holds one chat. The chat holds a sent request with the reference "notes.md", and its request area holds the reference "budget.xlsx", which the user named and did not send. The folder "C:\ projects\alpha" holds both files.
- **When:** The user removes "Alpha", and opens that chat among the ungrouped chats.
- **Then:**
  - The conversation still shows the sent request with "notes.md" as the user's message.
  - The request area still shows "budget.xlsx", in a state that says it cannot be read.
  - The request is not sent while that reference is in it, and the user can remove the reference or add the file as an attachment.
  - The system reads no file of "C:\ projects\alpha" for either reference without an approval of the user (FR-076).
  - The folder "C:\ projects\alpha" holds the same two files as before.
- **Check:** deterministic

## Notes

- A reference does not count toward attachment number limits [BR-001]. Safe read limits are checked when the reference is used and are separate from attachment limits.
- Naming a reference is a different way to complete the request from attaching a file. An attachment is a file the user adds to the request; a reference names material of the project folder.
- A reference that was sent stays in the conversation as the user's message. The product keeps no copy of the file it names: the file stays where the user keeps it, and an attachment the user added stays with its request (FR-049).
- A reference names material of the project folder. It reaches no saved work of a chat and no data of another chat.
- A chat of a removed workspace belongs to no workspace and has no project folder, so the user names no new reference in it. The system deletes no reference the chat already holds: one the user did not send stays in the request area, in a state that says it cannot be read, and one the user sent stays in the conversation (FR-073). A file of the former folder is read only with the approval of the user (FR-076, FR-077).
