---
id: FR-082
title: "Name a reference in the workspace as material"
---

## Requirement

- **Statement:** The user can name a file or a folder in the workspace of the chat as material for a request, as a reference. The system shows the reference in the request area, with its name and its state. It does not send the reference and does not read it while the user prepares the request. Naming a reference raises no permission of the chat; the agent reads it within the permission of the chat, when a request uses it [NFR-003]. Naming a reference adds no attachment [BR-001]. When the named file or folder cannot be read, for example it is missing or access was taken away, the system shows that state with the reason, as it shows the reason on an attachment it rejects. A reference whose state does not block sending can be sent alone, with no request text and no attachment (FR-015). A reference whose state blocks sending blocks the request like a rejected attachment (FR-015, FR-017).

## Acceptance conditions

### AC-1 · The reference is shown with name and state

- **Given:** The chat belongs to a workspace whose folder holds the file "notes.md". The request area holds no request text.
- **When:** The user names "notes.md" as material for the request.
- **Then:**
  - The request area shows the reference with its name "notes.md" and its state.
  - The conversation shows no new user's message, and nothing was sent.
- **Check:** deterministic

### AC-2 · Naming is not sending and not reading

- **Given:** The state after AC-1. A test account with the selected model's provider records each request it receives. The system has produced no plan for any request.
- **When:** The user names the reference and does not send a request.
- **Then:**
  - The provider receives no request, and the system starts no work. The content of "notes.md" joins the data of the request only when a request uses it.
- **Check:** deterministic

### AC-3 · Naming gives no permission

- **Given:** The state after AC-1. The computer holds a folder outside the workspace of the chat, with the file "secret.md" in it. No request of the chat names that folder.
- **When:** The user names "notes.md" as material, and sends a request that uses it.
- **Then:**
  - The permission of the chat is the same as before the naming (FR-077, NFR-003).
  - The work reads nothing of that folder outside the workspace, and no step there is done without an approval (FR-076).
- **Check:** deterministic

### AC-4 · An unreadable reference shows its state with the reason

- **Given:** The workspace folder of the chat holds no file "old.md", and the user names it.
- **When:** The system records the naming.
- **Then:**
  - The request area shows the reference "old.md" in a state that says it cannot be read, with the reason when it is known, as a rejected attachment shows its reason.
- **Check:** deterministic

### AC-5 · A ready reference can be sent alone

- **Given:** The state after AC-1. The reference is in a state that does not block sending.
- **When:** The user sends the request with the reference and no request text.
- **Then:**
  - The request is sent. The conversation shows the reference as the user's message.
- **Check:** deterministic

### AC-6 · A blocking reference blocks the request

- **Given:** The state of AC-4. The reference "old.md" is in a state that blocks sending. The request area holds no other content.
- **When:** The user tries to send the request.
- **Then:**
  - Nothing is sent, and the reference stays in the request area with its state.
- **Check:** deterministic

## Notes

- Whether the attachment count and size limits [BR-001] count for a file a request reads as a reference, and from which moment, are open questions in the design backlog of the ideal spec.
- Naming a reference is a different way to complete the request from attaching a file. An attachment is a file the user adds to the request; a reference names workspace material.
