---
id: FR-077
title: "Limit the reach of the agent of a chat by default"
---

## Requirement

- **Statement:** A new chat holds a permission limited to the project folder of its workspace and to the data of its requests. That permission lets the agent find and read the files of the user in the project folder, also when no request names them. Reading one makes it part of the data of the request. The permission covers what the work creates for the chat, such as the outline, the deck and a summary. DeckAgent saves that work for the chat as the work goes, and no approval is asked for the saving. The permission gives nothing more: the agent reaches the work DeckAgent saves for the chat only through what DeckAgent lets a request do. A step that reads outside the project folder needs the approval of the user (FR-076). So does a write outside the chat. A file the user gave as an attachment, or named as a reference, is part of the data of the request (FR-082). The agent never reaches the data of another chat, also not when both chats share a workspace. No approval gives it that reach, and when the work needs that data, the system says that it cannot reach it. The agent never changes, overwrites or deletes a file the user gave or a file of the user in the project folder, and it creates no file there (FR-084). Full access to the computer is never a permission the system sets by itself. No content of a request, an attachment or a file raises the permission of the chat. No permission raised in another chat raises this one.
- **Updated at:** 26-10-2026

## Acceptance conditions

### AC-1 · A new chat holds the limited permission

- **Given:** A new chat in a workspace whose project folder holds files. A second chat of the same workspace holds a conversation and a deck.
- **When:** The user opens the permission of the chat (FR-075).
- **Then:**
  - The permission shown covers the files of the user in the project folder of the workspace, the data of its requests, and what the work creates for the chat.
  - It covers no place outside that folder, and no part of the second chat.
- **Check:** judged

### AC-2 · Work reads the project folder without an approval

- **Given:** The project folder of the workspace of the chat holds a report "revenue-q4.md" beside twelve other files. No request of the chat names any of them.
- **When:** The user sends a request that asks for the revenue report of the quarter, and names no file.
- **Then:**
  - The work reads the files of the user in the project folder, and uses "revenue-q4.md" in its result.
  - No approval was asked for a file of the user in the project folder.
- **Check:** deterministic

### AC-3 · Beyond the project folder needs an approval

- **Given:** The state after AC-1. The computer holds a folder outside the project folder of the workspace. No request of the chat named it, and the user gave no approval for it.
- **When:** The work on a request needs to read a file there, or to write a file outside the chat.
- **Then:**
  - No step there is done without an approval of the user (FR-076).
  - A refused step and a step with no answer are not done (FR-076).
- **Check:** deterministic

### AC-4 · No reach into another chat, with or without an approval

- **Given:** Two chats X and Y in the same workspace. Y holds a conversation, a deck and an attachment. The user works on a request in X.
- **When:** The request, an attachment of it, or the work of X asks the system to read the conversation, the deck or the attachments of Y. The user also tries to approve such a step.
- **Then:**
  - The system reads nothing of Y, and the step is not done.
  - The response says that this data is out of reach, and that no approval gives it.
- **Check:** judged

### AC-5 · Originals stay and results stay apart from them

- **Given:** The state after AC-2. The work also creates a result for the chat, such as a changed deck and a summary of the conversation.
- **When:** The work saves its results.
- **Then:**
  - Each file the user gave as an attachment or named as a reference is the same as before the work. So is each file of the user in the project folder of the workspace.
  - No file was created, changed or deleted in the project folder.
  - The saved deck and the summary stay with the chat.
- **Check:** deterministic

### AC-6 · Saving the work needs no approval of its own

- **Given:** The state after AC-2. The project folder of the workspace holds the files of the user. The chat holds a deck and a summary saved for it. A second chat of the same workspace holds a deck.
- **When:** The work builds slides, changes a slide, and summarizes the conversation.
- **Then:**
  - The deck of the chat holds the slides and the change, and the summary is kept for the chat.
  - No approval was asked for saving any of them.
  - Each file of the user in the project folder is as it was, and no file appeared in it.
  - The deck of the second chat is as it was.
- **Check:** deterministic

## Notes

- What a new chat holds by default beyond its workspace and its data, and which named permissions exist, are open questions in the design backlog of the ideal spec. This requirement sets the boundary, not the names.
- A workspace groups the chats of one project folder, so the files of the user in that folder are inside the permission of each of those chats. A reference outside the folder joins the data of a request when a request reads it (FR-082).
- The project folder of a workspace holds the files of the user. The work DeckAgent saves for its chats — their conversations, their outlines, their decks and their summaries — is kept for the chats and stays available when that folder does not. That is why the system writes no file of it into the folder (FR-084).
- The default workspace has no project folder, so the permission of a chat in it covers the data of its requests, and reads no folder. The saved work of its chats stays available with no folder (FR-072).
- That no run ever reaches beyond the permission is measured by NFR-003 and NFR-004. What the agent sends outside the computer is NFR-007.
