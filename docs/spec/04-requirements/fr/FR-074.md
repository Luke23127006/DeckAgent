---
id: FR-074
title: "Reach a workspace folder that cannot be read"
---

## Requirement

- **Statement:** When the folder of a set-up workspace cannot be read, for example it was moved, deleted, or access was taken away, the system says so and says which workspace it belongs to. It says what the user can do, for example put the folder back or give access again. It deletes no chat, no conversation and no deck, and the chats of that workspace stay reachable, as FR-073 says for the chats of a removed workspace. The system invents no reason and claims no cause it does not know.

## Acceptance conditions

### AC-1 · The missing folder is reported with its workspace

- **Given:** The workspace "Alpha" is set up for the folder "C:\ projects\alpha" and holds one chat with a deck.
- **When:** The folder is deleted outside DeckAgent, and the user works in DeckAgent again.
- **Then:**
  - The system says that the folder of "Alpha" cannot be read, and names "Alpha".
- **Check:** deterministic

### AC-2 · Nothing is deleted

- **Given:** The state after AC-1.
- **When:** The user then opens the chats the user can open (FR-048), without restoring the folder.
- **Then:**
  - The chat of "Alpha" is reachable, with its conversation and its deck.
  - The system changes and deletes no chat, conversation or deck.
- **Check:** deterministic

### AC-3 · The user is told what to do next

- **Given:** The state after AC-1.
- **When:** The user reads the response of the system.
- **Then:**
  - The response says what the user can do, for example put the folder back or give access again.
- **Check:** judged

## Notes

- Whether adding the same folder again binds the chats of the removed or unreachable workspace is an open question in the design backlog of the ideal spec.
