---
id: FR-017
title: "Reject an attachment the system cannot use"
---

## Requirement

- **Statement:** The system rejects an added file that breaks the attachment rule [BR-001], or that is protected, damaged or unreadable. It rejects the file when the user adds it, and shows the reason on the attachment at once. The attachment stays until the user removes it, and the rest of the request stays as it was. Choosing another model changes the state of no attachment.
- **Status:** confirmed
- **Source:** use case flow, and owner decision, 2026-10-09: a file is rejected when it is added, not when the request is sent; owner decision, 2026-10-12: DeckAgent decides which attachments it accepts, and the selected model changes no attachment state
- **Updated at:** 12-10-2026

## Acceptance conditions

### AC-1 · File that breaks the attachment rule

- **Given:** A chat with no active request. The request area holds the request text "a talk from these notes" and the ready attachment "notes.docx".
- **When:** The user adds a file larger than the size the attachment rule allows.
- **Then:**
  - Before the user sends anything, the new attachment shows the state rejected, with a reason.
  - "notes.docx" and the request text are unchanged.
- **Check:** deterministic

### AC-2 · Protected or damaged file

- **Given:** A chat with no active request. The request area is empty.
- **When:** The user adds a document protected by a password and a damaged file.
- **Then:**
  - Before the user sends anything, each of the two attachments shows the state rejected, with a reason.
- **Check:** deterministic

### AC-3 · Type the system does not accept

- **Given:** A chat with no active request. The request area is empty.
- **When:** The user adds a file of a type that the attachment rule does not accept [BR-001].
- **Then:**
  - Before the user sends anything, the attachment shows the state rejected, with a reason.
- **Check:** deterministic

### AC-4 · Reason names the cause

- **Given:** The states after AC-1, AC-2 and AC-3.
- **When:** The user reads the reason on each rejected attachment.
- **Then:**
  - The reason for the large file says that it is too large.
  - The reason for the protected document says that it is protected.
  - The reason for the damaged file says that it cannot be read.
  - The reason for the file of AC-3 says that its type is not accepted.
- **Check:** judged

### AC-5 · Rejected attachment stays until removed

- **Given:** The state after AC-1.
- **When:** The user adds more request text and another ready file, and does not remove the rejected attachment.
- **Then:**
  - The rejected attachment is still in the request area, with its reason.
  - The added request text and file are in the request area.
- **Check:** deterministic

### AC-6 · Choosing a model changes no attachment

- **Given:** A chat with no active request and the selected model M1. Another model M2 is selectable. The request area holds the request text "a talk on these charts". It also holds the ready attachment "chart.png" and the rejected attachment "big.pdf", too large.
- **When:** The user chooses M2. The user then chooses M1 again.
- **Then:**
  - After each choice, "chart.png" shows the state ready.
  - After each choice, "big.pdf" shows the state rejected, with the same reason.
  - The request text is unchanged.
- **Check:** deterministic

## Notes

- A file that the system accepts but that has nothing usable is not rejected here. FR-009 covers it.
- A rejected attachment blocks sending. FR-015 covers it.
- Until 2026-10-12, this requirement also rejected a file of a type the selected model could not read. It checked each attachment again when the user chose another model. The owner decision of 2026-10-12 removed both.
