id: FR-042
title: "Run each request with the selected model of its chat"
---

## Requirement

- **Statement:** Each chat has its own selected model. A request runs with the model selected in its chat when the request starts. It uses the provider configuration of that model, with its provider ID and its saved settings, such as the key. The request keeps that model until it ends, also for an answer the user gives to it. A later choice applies only to requests that start after it.
- **Status:** confirmed
- **Source:** use case flow, and owner decision, 2026-10-12: each chat keeps its own selected model, and a model chosen while a request is active applies to the next request; owner decision, 2026-10-12: a selected model belongs to one provider configuration, and each provider ID has one saved provider configuration
- **Updated at:** 12-10-2026

## Acceptance conditions

### AC-1 · The request goes to the selected model

- **Given:** A provider configuration for provider P is saved with the key K1. Its added models are M1 and M2. Chat X has the selected model M1. A test account with P records each request it receives. Chat X has no active request.
- **When:** The user sends the request "a talk on our pilot results" in chat X.
- **Then:**
  - P receives the request for model M1 with the key K1.
- **Check:** deterministic

### AC-2 · Each kind of work uses the selected model

- **Given:** The state of AC-1. The system has shown an outline proposal.
- **When:** The user confirms the outline. After the slides are built, the user sends "make slide 2 shorter".
- **Then:**
  - P receives the confirmation for model M1 with the key K1.
  - P receives the change request for model M1 with the key K1.
- **Check:** deterministic

### AC-3 · A replaced key is used next

- **Given:** The state of AC-1. The user then replaced the key of the provider configuration with K2. M1 is still an added model.
- **When:** The user sends a new request in chat X.
- **Then:**
  - P receives the request for model M1 with the key K2.
  - No later request uses K1.
- **Check:** deterministic

### AC-4 · A choice during a request applies to the next request

- **Given:** The state of AC-1. The system works on request R1 in chat X. R1 started with M1.
- **When:** The user chooses M2 in chat X. R1 then ends, and the user sends "add a slide on costs".
- **Then:**
  - Every request P receives for R1 is for model M1.
  - The system shows that it works on R1 until R1 ends.
  - P receives "add a slide on costs" for model M2.
- **Check:** deterministic

### AC-5 · An answer keeps the model of its request

- **Given:** The state of AC-1. Request R1 in chat X started with M1. The system asked a question and waits for the user's answer.
- **When:** The user chooses M2 in chat X, then answers the question. After R1 ends, the user sends a new request.
- **Then:**
  - The answer is part of R1. No other request starts for it.
  - Every request P receives for R1, also after the answer, is for model M1.
  - P receives the new request for model M2.
- **Check:** deterministic

### AC-6 · Confirming the outline starts a request with the current choice

- **Given:** The state of AC-1. The system drafts an outline in chat X with M1. Meanwhile the user chooses M2. The system then shows the outline proposal, and that request ends.
- **When:** The user confirms the outline.
- **Then:**
  - P receives the work on the confirmed outline for model M2.
- **Check:** deterministic

### AC-7 · Each chat keeps its own selected model

- **Given:** The state of AC-1. Chat Y has the selected model M2. The user is in chat Y. No request is active.
- **When:** The user opens chat X and sends "make slide 2 shorter".
- **Then:**
  - Chat X shows M1 as its selected model.
  - P receives the request for model M1.
  - Chat Y still has M2 as its selected model.
- **Check:** deterministic

### AC-8 · The same model ID in two provider configurations

- **Given:** "Work AI" connects to provider P with the key K1. "Lab" is a custom model API with the provider ID "lab", the base URL U1 and the key K2. Each has the added model M1. Chat X has M1 of "Work AI" as its selected model. Chat Y has M1 of "Lab". Test accounts with P and at U1 record each request and its key.
- **When:** The user sends a request in chat X. After it ends, the user sends a request in chat Y.
- **Then:**
  - P receives the request of chat X for model M1 with the key K1. U1 receives no request for it.
  - U1 receives the request of chat Y for model M1 with the key K2. P receives no request for it.
- **Check:** deterministic

## Not specified

- Which settings an active request uses after the user saves a new key or base URL for its provider configuration. Pending owner decision.

## Notes

- Choosing the selected model is covered by FR-055. A chat with no selected model, or with one that is no longer selectable, is covered by FR-056. The selected model of a new chat is covered by FR-053.
- One request is active at a time, as FR-014 says. An answer to a question is part of the same request, as FR-020 says.
- Until 2026-10-12, this requirement said that the one model set up runs every request. It also said that the user chooses no model. It followed the owner decisions of 2026-10-11 (one working model) and 2026-10-12 (no switching between models). The owner decision of 2026-10-12 on the selected model of each chat replaced them.
- Until 2026-10-12, AC-8 used two provider configurations for one provider. The owner decision of 2026-10-12 on provider IDs allows one for each provider ID. AC-8 now uses a custom model API.
