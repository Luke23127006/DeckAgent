---
id: FR-076
title: "Approve a step of the work that goes beyond the permission"
---

## Requirement

- **Statement:** When a step of the work goes beyond the permission of the chat, the system does the step only after the user approves it. It names the step, the data or files it touches, and why it goes beyond the permission. An approval given covers that step once, within what the user allowed. If the user refuses the step, or does not answer yet, the system does not do it: it says what it did instead, what the request still needs, and it can propose a safer way that stays within the permission. A step with no answer is not done while nothing permits it. The request stays open, the system works on nothing past the step, and no new request starts in the chat while it waits (FR-014). The user can answer later, or stop the request instead (FR-018). The system offers a permission that lasts only when it names in plain words what it covers and its scope; the user confirms before it applies, and takes it back as a saved change of the permission (FR-075). A question the agent asks to clarify the instruction is not an approval; it permits nothing.

## Acceptance conditions

### AC-1 · The ask names the step and the reason

- **Given:** A chat with the default permission (FR-077). The work on a request reaches a step that reaches outside the permission of the chat.
- **When:** The system needs the step to go on.
- **Then:**
  - The response names the step, the data or files it touches, and why the step goes beyond the permission.
  - The response asks the user to allow it once or to refuse it.
- **Check:** judged

### AC-2 · One approval does the step once

- **Given:** The state after AC-1.
- **When:** The user allows the step once.
- **Then:**
  - The system does the step. It does nothing beyond what the user allowed.
  - A later step that again goes beyond the permission is asked for again; it is not done because of the earlier approval.
- **Check:** deterministic

### AC-3 · A refused step is not done

- **Given:** The state after AC-1.
- **When:** The user refuses the step.
- **Then:**
  - The system does not do the step.
  - The response says what it did instead, and what the request still needs.
- **Check:** deterministic

### AC-4 · A step with no answer waits, and does nothing

- **Given:** The state after AC-1. The user does not answer.
- **When:** Time passes while the request stays open.
- **Then:**
  - The step is not done, and nothing else of the work proceeds past it.
  - The request is still active and waits, as FR-020 says.
  - When the user answers, AC-2 or AC-3 applies. When the user stops the request, FR-018 applies.
- **Check:** deterministic

### AC-5 · A permission that lasts is named and confirmed

- **Given:** The state after AC-1. The system offers a permission that lasts.
- **When:** The user reads the offer.
- **Then:**
  - The offer names in plain words what that permission covers and its scope. Without that naming, the offer is not made.
  - It applies only after the user confirms it. The user can take it back by a saved change of the permission (FR-075).
- **Check:** deterministic

## Notes

- How long a permission that lasts holds, and how the user keeps an overview of every one of them, are open questions in the design backlog of the ideal spec.
- Which name the product gives a permission that lasts depends on the open list of named permissions; the ask itself stays as this requirement states it.
