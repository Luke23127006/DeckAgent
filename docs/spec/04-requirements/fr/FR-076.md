---
id: FR-076
title: "Approve a step of the work that goes beyond the permission"
---

## Requirement

- **Statement:** When a step of the work goes beyond the permission of the chat, the system does the step only after the user approves it. It names the step, the data or files it touches, and why it goes beyond the permission. An approval given covers that step once, within what the user allowed. If the user refuses the step, the system does not do it: it says what it did instead, what the request still needs, and it can propose a safer way that stays within the permission. The refusal is an answer of the user, so the request waits on that approval no longer and the system asks for that step no more. The system goes on with the steps that stay within the permission; when the request cannot be finished without the refused step, it says so. If the user does not answer yet, the system does not do the step either, and it says that it waits for the user's answer. It reports no choice the user did not make. While it waits on that answer, the request stays open, the system works on nothing past the step, and no new request starts in the chat (FR-014). The user can answer later, refuse, or stop the request instead (FR-018). The system offers a permission that lasts only when it names in plain words what it covers and its scope; the user confirms before it applies, and takes it back as a saved change of the permission (FR-075). A continuing approval covers only the named scope and the same chat [BR-009]. The system keeps that approval until the user revokes it. It does not expand the permission of a different chat. No approval allows changing an original project file or reading another chat's data. A question the agent asks to clarify the instruction is not an approval; it permits nothing.

## Acceptance conditions

### AC-1 · The ask names the step and the reason

- **Given:** A chat with the default permission (FR-077). The work on a request reaches a step that reaches outside the permission of the chat.
- **When:** The system needs the step to go on.
- **Then:**
  - The response names the step, the data or files it touches, and why the step goes beyond the permission.
  - The response asks the user to allow it once or to refuse it.
- **Check:** judged

### AC-2 · One approval does the step once

- **Given:** The state after AC-1.
- **When:** The user allows the step once.
- **Then:**
  - The system does the step. It does nothing beyond what the user allowed.
  - A later step that again goes beyond the permission is asked for again; it is not done because of the earlier approval.
- **Check:** deterministic

### AC-3 · A refused step is not done

- **Given:** The state after AC-1.
- **When:** The user refuses the step.
- **Then:**
  - The system does not do the step.
  - The response says what it did instead, and what the request still needs.
  - The request waits on that approval no longer, and the system asks for the step no more.
  - The work goes on only within the permission. When the request cannot be finished without the refused step, the response says so.
- **Check:** deterministic

### AC-4 · A step with no answer waits, and does nothing

- **Given:** The state after AC-1. The user does not answer.
- **When:** Time passes while the request stays open.
- **Then:**
  - The step is not done, and nothing else of the work proceeds past it.
  - The request is still active and waits, as FR-020 says.
  - The response says that it waits for the user's answer. It does not say that the step was refused, and it reports no choice the user did not make.
  - When the user answers, AC-2 or AC-3 applies. When the user stops the request, FR-018 applies.
- **Check:** judged

### AC-5 · A permission that lasts is named and confirmed

- **Given:** The state after AC-1. The system offers a permission that lasts.
- **When:** The user reads the offer.
- **Then:**
  - The offer names in plain words what that permission covers and its scope. Without that naming, the offer is not made.
  - It applies only after the user confirms it. The user can take it back by a saved change of the permission (FR-075).
- **Check:** deterministic

### AC-6 · A continuing approval is limited to one chat

- **Given:** The user approved a named outside-file read scope for Chat X. Chat Y does not have that approval.
- **When:** A later request of Chat X reads the same outside file, and a request of Chat Y asks to read it.
- **Then:**
  - Chat X can read the file within the saved scope.
  - Chat Y still needs its own approval.
  - Neither chat can read the saved work of the other chat.
- **Check:** deterministic

## Notes

- A continuing approval holds for the named scope and its chat [BR-009]. The user reviews and revokes it through FR-075.
- Which name the product gives a permission that lasts depends on the named permissions of [BR-009]; the ask itself stays as this requirement states it.
