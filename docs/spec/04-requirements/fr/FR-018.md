---
id: FR-018
title: "Stop a request"
---

## Requirement

- **Statement:** The user can stop an active request, also while the system waits for an answer. After the stop, the system no longer works on the request and shows a notice that the response was interrupted. It keeps the request in the conversation and never sends it again by itself. A later request is new work, not a resumed run of the stopped one.
- **Status:** confirmed
- **Source:** use case flow, and owner decision, 2026-10-11: after a stop, the user carries on through a new request in the conversation
- **Updated at:** 12-10-2026

## Acceptance conditions

### AC-1 · Stop is offered while the system works

- **Given:** The user sent the request "a talk on our pilot results". The system works on it.
- **When:** The user looks for a way to end the work.
- **Then:**
  - The user can stop the request.
- **Check:** deterministic

### AC-2 · Stop ends the work on the request

- **Given:** The state of AC-1.
- **When:** The user stops the request, and the system shows that the stop took effect.
- **Then:**
  - The system no longer shows that it works on the request.
  - The user's message is still in the conversation, the same as when it was sent.
  - After the stop takes effect, the conversation shows no further response content for the stopped request.
  - After the stop takes effect, the stopped request creates no slide and changes no slide.
  - The system never sends the stopped request again or resumes its work by itself.
  - The user can send a new request.
- **Check:** deterministic

### AC-3 · Notice says the response was interrupted

- **Given:** The state of AC-2.
- **When:** The user reads the conversation.
- **Then:**
  - A notice says that the response to the request was interrupted.
  - The notice does not say that the work failed.
- **Check:** judged

### AC-4 · Stop while the system waits for an answer

- **Given:** The request is "a talk on our pilot". The system asked who the audience is and waits for the answer.
- **When:** The user stops the request.
- **Then:**
  - The system no longer waits for an answer.
  - The question and the user's request are still in the conversation, the same as before.
  - The conversation shows a notice that the response was interrupted.
  - A message the user sends next starts a new request. It is not an answer to the question.
- **Check:** deterministic

### AC-5 · New request after a stop is new work

- **Given:** The state of AC-2.
- **When:** The user sends "go on with the remaining work".
- **Then:**
  - The conversation shows it as a new user's message.
  - The stopped request shows once in the conversation. It is not sent again.
  - The system works on the new request.
- **Check:** deterministic

## Not specified

- How soon the work ends after the user stops it. Pending owner decision.

## Notes

- What the work produced before the stop took effect, such as finished slides, is not covered here. The requirements of that work cover it.
- The notice and the state that show the stop are not further work of the stopped request. AC-2 does not forbid them.
- AC-2 holds with no time limit. A test observes the chat for a finite time, which checks the condition but does not limit it.
