---
id: FR-020
title: "Wait for the user's answer within the request"
---

## Requirement

- **Statement:** When the work needs an answer, the system keeps the request active and says that it waits for the answer. Each reply, typed or chosen as a suggested option, joins the same request and starts no new request. The system goes on when nothing open changes the result a lot. Otherwise it asks again, and it never chooses between such meanings for the user.
- **Updated at:** 25-10-2026

## Acceptance conditions

### AC-1 · Waiting is shown

- **Given:** A chat with no deck. The request is "a talk on our pilot", with no material. The system asked who the audience is.
- **When:** The system waits for the answer.
- **Then:**
  - The conversation says that the system waits for the user's answer.
  - The system does not show that it works.
  - The request is still active. The user can stop it.
- **Check:** deterministic

### AC-2 · Typed reply joins the request

- **Given:** The state of AC-1.
- **When:** The user replies "hospital board members".
- **Then:**
  - The reply shows in the conversation as the user's message.
  - The reply is part of the request that asked.
  - No second request starts.
  - The system goes on with the work of that request.
- **Check:** deterministic

### AC-3 · Reply through a suggested option

- **Given:** The state of AC-1. The system offered answers as suggested options.
- **When:** The user chooses one of them.
- **Then:**
  - The outcomes are the same as in AC-2.
- **Check:** deterministic

### AC-4 · Settled answer gets no further question

- **Given:** The state of AC-1.
- **When:** The user replies "hospital board members, most of them doctors".
- **Then:**
  - The system asks nothing more about the audience.
  - It goes on with the work.
- **Check:** judged

### AC-5 · Reply that settles nothing stays in the request

- **Given:** The conversation shows proposals A and B. B is the current outline. The system asked whether the user wants to confirm B or keep revising it, and waits for the answer.
- **When:** The user replies "maybe".
- **Then:**
  - The reply shows in the conversation as the user's message, as part of the request that asked.
  - No second request starts.
  - No outline proposal is confirmed.
  - The request is still active. The user can stop it.
- **Check:** deterministic

### AC-6 · Open meaning is not chosen for the user

- **Given:** The state after AC-5.
- **When:** The system responds to the reply.
- **Then:**
  - The system asks again about what stays open. The question still helps the user choose between confirming B and revising it.
  - The system does not take the reply as a confirmation or as an instruction to revise.
  - The system does not state an assumption in place of the user's choice.
- **Check:** judged

## Notes

- The use case that includes the request says what the system asks. This requirement covers the wait and the replies. The question itself is covered by the requirements of that work.
- Stopping the request while the system waits is covered by FR-018.
- There is no fixed number of questions. AC-6 holds however many questions came before the reply.
