---
id: FR-080
title: "Export the session of a chat"
---

## Requirement

- **Statement:** The user can export the session of a chat as a conversation file or as a session archive. The conversation file is one readable file for reading. It holds the requests, the responses, the questions asked to clarify, the outline proposals, the confirmed outline, the decisions recorded and the results. The session archive is one packaged file for review or handover. Before the system writes the archive, it says what the archive holds. It holds what the session needs for that: the conversation, the records of the requests and their activities, the outline and the deck state, and the attachments that belong to the session. It packs no file of the user that the session does not use, no file named only as a reference that a request never read, no copy of the project folder of the workspace, and no other file that only served the system to make the slides. No export holds a key, a token or another credential that DeckAgent keeps, and the system checks the records it writes for them [NFR-006]. Content the user gave stays as the user gave it: the export removes no part of it, and the product promises no search for a secret inside it. The user chooses where the file goes (FR-085). An export needs no project folder: it writes the session DeckAgent saved, so a folder that cannot be read takes nothing out of the export and is not read again for it. When a part of the saved session that the export needs cannot be read, the system gives no finished file, says that the export failed, and says why when the reason is known. No export changes the chat. When the system fails while it prepares or saves the file, for example no room to save, it gives no file, says that the export failed, and says why when the reason is known; it never says that an export is complete when it is not, and the user can start the export again. When the chat holds no sent request, exporting says that there is nothing to export and writes no file. The product imports no archive and builds no chat from one.
- **Updated at:** 26-10-2026

## Acceptance conditions

### AC-1 · The conversation file holds the conversation and its results

- **Given:** A chat with two sent requests, an outline that was drafted and confirmed, a deck of five slides, one clarifying question with the answer of the user, and one decision recorded in the conversation.
- **When:** The user exports the conversation and chooses where the file goes.
- **Then:**
  - The system gives one readable file that holds the two requests, the responses, the clarifying question with its answer, the outline proposals, the confirmed outline, the recorded decision and the results of the work.
  - The response says where the file is.
  - The chat, its conversation and its deck are unchanged.
- **Check:** deterministic

### AC-2 · The archive announces what it holds, then holds it

- **Given:** The state of AC-1. The requests have recorded activities. The project folder of the workspace holds one file that no request of the chat read, and one file was named as a reference that no request read.
- **When:** The user chooses to export the session archive.
- **Then:**
  - Before it writes the file, the response says what the archive holds.
  - The archive holds the conversation, the records of the requests and their activities, the outline and the deck state, and the attachments that belong to the session.
  - The archive holds neither the file that no request read nor the reference that a request never read.
  - The archive holds no copy of the project folder.
- **Check:** deterministic

### AC-3 · No credential DeckAgent keeps in an export

- **Given:** The state of AC-1. A provider configuration with the key K1 is saved. The chat holds an attachment A1, which the user gave, and whose text holds the words "password: hunter2".
- **When:** The user exports the conversation and, in another run, the session archive.
- **Then:**
  - Neither file holds K1 or any part of it [NFR-006].
  - The archive holds A1 as the user gave it. The response claims no removal of a secret from that content.
- **Check:** deterministic

### AC-4 · A failed export gives no file

- **Given:** The state of AC-1. The destination cannot take the file, for example it is full.
- **When:** The user exports the conversation and, in another run, the session archive.
- **Then:**
  - No finished file is written.
  - The response says that the export failed, and why when the reason is known. It never says that the export is complete.
  - The chat is unchanged, and the user can start the export again.
- **Check:** deterministic

### AC-5 · No sent request, nothing to export

- **Given:** A chat with no sent request.
- **When:** The user chooses to export the conversation, or the session archive.
- **Then:**
  - The response says that there is nothing to export, and writes no file.
- **Check:** deterministic

### AC-6 · An export needs no project folder

- **Given:** A chat with two sent requests and a deck of five slides, in a workspace whose project folder was deleted outside DeckAgent. The chat, its conversation and its deck stay readable.
- **When:** The user exports the conversation and, in another run, the session archive.
- **Then:**
  - Each export gives its file, and the response says where it is.
  - No export says that it needed a file of the project folder.
  - The chat, its conversation and its deck are unchanged.
- **Check:** deterministic

### AC-7 · A part of the saved session that cannot be read fails the export

- **Given:** The state of AC-1. In this test, a part of the session that the archive needs cannot be read.
- **When:** The user exports the session archive.
- **Then:**
  - No finished archive is given.
  - The response says that the export failed, and why when the reason is known.
  - It never says that the export is complete, and claims no content it cannot read.
  - The chat is unchanged, and the user can start the export again.
- **Check:** deterministic

## Notes

- Which parts of a session the archive holds beyond the minimum above, what counts as a recorded decision, and how an export file is named, are open questions in the design backlog of the ideal spec. So is whether an export warns about content the user gave that holds a secret.
- Getting the deck as an editable or a fixed file is a different export, and this requirement does not replace it. That the product imports no archive is a boundary of the ideal product; the flow ID of that unselected behavior is retired.
- Where the file goes, that no existing file is replaced, and that a cancelled export writes nothing are FR-085.
- What an export holds is bounded by NFR-006; that the file stays on the computer is bounded by NFR-007. Which credentials DeckAgent keeps, and how the check finds them, are architecture matters.
