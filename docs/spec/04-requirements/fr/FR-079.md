---
id: FR-079
title: "Compact the conversation"
---

## Requirement

- **Statement:** The user can choose to compact the conversation of a chat. Compacting summarizes the earlier conversation, and later requests work with the summary. The system says what compacting does before it compacts, and says where the summary starts. It keeps the outline, the confirmed outline, the deck, the attachments and the decisions of the chat, and takes none of them away. The whole conversation stays readable in the chat and exportable (FR-080). The summary is not the conversation word for word; the system promises no detail of the conversation that the summary does not keep, and the user reads no loss because the whole conversation stays readable. Only the user starts a compact. When a request in the chat is active, also one that waits for an answer, the system compacts nothing and schedules no compact; it says that the user can compact after the request ends. When compacting fails, the system says so, and why when it knows, and changes no conversation, summary, outline, deck or attachment; the user can start compacting again.

## Acceptance conditions

### AC-1 · Compacting keeps what the chat holds

- **Given:** A chat with a conversation, an outline proposal, a confirmed outline, a deck with five slides, two attachments and decisions recorded in the conversation. No request is active.
- **When:** The user chooses to compact and compacting succeeds.
- **Then:**
  - Later requests work with the summary of the earlier conversation.
  - The conversation of the chat is still readable in full, with every message before the compact.
  - The outline proposal, the confirmed outline, the five slides, the attachments and the recorded decisions are unchanged.
  - The response says where the summary starts.
- **Check:** deterministic

### AC-2 · The user is told what compacting does

- **Given:** The state of AC-1.
- **When:** The user reads the response to the choice to compact.
- **Then:**
  - Before later requests work with the summary, the response says that compacting summarizes the earlier conversation and that later requests work with the summary.
- **Check:** judged

### AC-3 · No compact while a request is active, and none scheduled

- **Given:** The state of AC-1. A request R1 of the chat is active; in one run the system works on it, in another run it waits for the user's answer.
- **When:** The user chooses to compact.
- **Then:**
  - Nothing is compacted in either run, and the system schedules no compact.
  - The response says that the user can compact after the request ends.
  - R1 keeps running, or keeps waiting, as it did.
- **Check:** deterministic

### AC-4 · A failed compact changes nothing

- **Given:** The state of AC-1. The system cannot compact.
- **When:** The user chooses to compact.
- **Then:**
  - The response says that compacting did not happen, and why when the reason is known.
  - The conversation, the summary if one existed, the outline proposal, the confirmed outline, the deck and the attachments are unchanged.
  - The user can start compacting again. Nothing compacts by itself.
- **Check:** deterministic

## Notes

- Whether compacting asks the user before later requests work with the summary, and whether the system offers compacting of its own when the context is nearly full, are open questions in the design backlog of the ideal spec.
- How a summary is made and kept is an architecture matter. NFR-008 protects the last saved state of the chat.
