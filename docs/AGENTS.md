# Rules for `docs/`

These rules extend the root `AGENTS.md` for every file under `docs/`.

- **Placement.** Developer-facing conventions and reference go under `docs/development/`, agent guidance under `docs/agents/`, tooling guides under `docs/tooling/`, product specs under `docs/spec/`, decision records under `docs/adr/`, and research under `docs/research/`. Plans, tasks and handoffs live in GitHub Issues, not in `docs/`.
- **Writing.** Every file follows [`development/writing-documents.md`](development/writing-documents.md): living documents and records, outcomes and not the conversation, one line per paragraph, clickable links, no bare ID. Research notes also follow [`research/_STYLE.md`](research/_STYLE.md).
- **No plan detail in `docs/`.** A document under `docs/` holds no detail of an implementation plan. Plan detail means a task ID (`TASK-003`, `W-014`), a gate ID, the status of either, or the owner or date of one stage. Name the behavior or the rule instead, and let the GitHub Issue of the task cite this document. A document that copies a plan goes stale with it.
- **Standalone readability.** A reader must understand a file without opening another file to decode an ID. When a file cites another source, it says what the source shows in words (for example `claude-report (stop before any slide exists keeps an empty canvas)`), not by an opaque code such as `CS-01 B15` or `row 3.12`. Meaningful IDs that the project defines and resolves (`UC-001`, `A12`, `FR-004`) are fine; row or step numbers inside another document are not.
- **One research file per product**, named for the product (`open-design.md`), never for a sequence number. A question that spans products is split among their files. See [`research/_STYLE.md`](research/_STYLE.md).
- **Write once.** A behavior shared by several flows is written once, in a common section; each flow states only what differs.
- **Spec style.** Files in `docs/spec/` follow [`spec/_STYLE.md`](spec/_STYLE.md): plain words, short sentences, one action per line, keywords in bold, and no history. Use cases state intent and response and never name a control, gesture, position or look (rule 11). A design choice is written as its result, or `pending` while it is open, with no decision ID; a spec file states what a research note shows and does not link it.
- **Mermaid.** Readers use GitHub and VS Code 1.121 or later, which renders Mermaid in its built-in Markdown preview. Do not install the old Markdown Preview Mermaid Support extension; it is deprecated. Use the conservative subset in the `mermaid-markdown` skill and the rules in [`spec/_MERMAID.md`](spec/_MERMAID.md).
- **Use case diagrams are authoritative.** The interaction diagram of a use case draws the main flow, hand-written, and is the source of the text of each step; the Steps table holds the same steps in the same order. Nothing in `docs/spec/` is generated from other blocks; edit the diagram when the behavior changes.
